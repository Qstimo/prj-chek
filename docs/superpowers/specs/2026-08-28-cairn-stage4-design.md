# CAIRN — этап 4 «Переменные»: дизайн

Дата: 2026-08-28 · Статус: согласован · Основание: `project-registry-spec [eTsSSz].md`, раздел 10, пункт 4

## 1. Объём

Реализуется секция «Переменные» (ТЗ 3.3) — самая чувствительная сущность системы: конфигурация проекта по окружениям с шифрованием значений, версионированием, раскрытием отдельным действием и импортом/выгрузкой `.env`.

Этап закрывает открытый вопрос ТЗ (раздел 12) о глубине хранения версий: **версии хранятся все, без ограничения**. Масштаб системы — десятки проектов, версии — короткие строки; простота важнее экономии (ТЗ 9). Ограничение вводимо позже без миграции.

Второй смежный вопрос — «формат выгрузки конфигурации при деплое» — остаётся этапу 8: машинная выгрузка пойдёт через токены агентов, здесь появляется только человеческая выгрузка `.env`.

В объём не входит доступ агентов к значениям (этап 8, отдельная явная настройка токена — ТЗ 7.3).

## 2. Что уже есть и не меняется

- **Шифрование** — `CryptoService` этапа 1 (спека 4.9): AES-256-GCM, формат `v1:<nonce>:<ciphertext>:<tag>`, ключ в `CAIRN_ENCRYPTION_KEY` отдельно от базы, отказ старта без ключа. Применяется как есть; механизм отрабатывался на секретах TOTP намеренно ради этого этапа.
- **Модель прав**: секция `variables` в перечислении с этапа 1, проверка в репозитории, `404`/`403`, журнал в транзакции.
- **Окружения** этапа 2: переменная принадлежит окружению (ТЗ 3.3 «принадлежность окружению»).

## 3. Модель данных

Две таблицы.

### 3.1 variables

`id`, `environment_id`, `key`, `description`, `created_at`, `updated_at`.

`environment_id` — `ON DELETE RESTRICT`. Уникальный индекс по (`environment_id`, `key`): один ключ — одна переменная в окружении. Формат ключа — `[A-Z][A-Z0-9_]*` (стиль переменных окружения), проверяется схемой контракта.

`description` необязателен, но существует ради уровня «метаданные»: «разработчику почти всегда нужно знать, *какие* переменные требует проект» (ТЗ 4.3) — описание и отвечает на этот вопрос, не раскрывая значения.

Значения в этой таблице нет вовсе — только в версиях.

### 3.2 variable_versions

`id`, `variable_id`, `version_no`, `value_encrypted`, `created_by_subject_id`, `created_at`.

`variable_id` и `created_by_subjectId` — `restrict`. Уникальный индекс по (`variable_id`, `version_no`).

**Текущее значение — версия с наибольшим номером.** Указателя «текущая версия» нет намеренно: два источника правды (максимальный номер и указатель) могли бы разойтись. История линейна и только растёт:

- изменение значения — новая версия с номером `max + 1`;
- **откат** к версии N — тоже новая версия, значение которой равно значению N (журнал фиксирует «откат к N»); история не переписывается;
- правка описания или ключа версии не создаёт — версионируется значение, а не паспорт переменной.

**Удаление переменной** (уровень `write`) стирает её вместе со всеми версиями — явными строками в одной транзакции, каскадов нет (инвариант этапа 1 проверяется тестом). Секреты удалённой переменной — обуза, а не ценность: держать их вечно значило бы расширять поверхность утечки. Журнал хранит факт удаления и ключ.

**Удаление окружения**, у которого есть переменные, блокируется: репозиторий окружений получает проверку с понятным `409` («сначала удалите переменные»); ключ `restrict` страхует на уровне базы. Это обещание спеки этапа 2 (раздел 10).

## 4. Доступ

Секция `Section.Variables` (ТЗ 4.3, строка «Переменные»):

| Уровень | Доступно |
|---|---|
| нет строки выдачи | `404` на всех маршрутах |
| `metadata` | список: ключ, описание, номер текущей версии, даты |
| `read` | плюс раскрытие значения отдельным действием; история версий; выгрузка `.env` |
| `write` | создание, правка, удаление, откат, импорт `.env` |

Особенность секции: **проекция списка одинакова на всех уровнях** — значение не «подробность» объекта, а отдельная операция. `projectByLevel` здесь не используется; список никогда не содержит значений, на каком бы уровне ни был субъект (ТЗ 3.3: «значение никогда не попадает в общий список»).

Выгрузка `.env` отнесена к уровню `read` осознанно: это чтение, как и раскрытие одного значения, — а субъект с `read` и так соберёт тот же файл раскрытием по одному. Ограничение уровнем `write` лишь добавило бы шагов, не добавив защиты. Компенсация — журнал: выгрузка фиксируется отдельным действием с перечнем ключей.

Импорт и откат — только `write`, по матрице.

## 5. Раскрытие и журнал

Каждое чтение значения — отдельное действие с записью в журнал (ТЗ 3.3, 4.4):

- `POST …/variables/:id/reveal` (уровень `read`) → `{ value, versionNo }`; журнал `variable.revealed` с ключом, окружением и номером версии;
- `POST …/variables/:id/versions/:no/reveal` — раскрытие исторической версии, журналируется так же;
- `GET …/variables/export` → текст `.env` из текущих версий; журнал `variables.exported` с перечнем ключей и их числом.

**Значения не попадают в журнал ни при каком действии** (ТЗ 9): записи хранят ключи, номера версий и перечни полей. Раскрытие — POST, а не GET: у действия есть побочный эффект (запись в журнал), и кэширование или предзагрузка браузером здесь недопустимы.

Полный перечень действий журнала: `variable.created`, `variable.updated` (имена полей), `variable.deleted`, `variable.revealed`, `variable.rolled_back` (с номерами «с какой на какую»), `variables.imported` (ключи), `variables.exported` (ключи).

## 6. API

Вложенно в окружение:

| Метод | Маршрут | Право | Ответ |
|---|---|---|---|
| `GET` | `…/environments/:eid/variables` | `metadata` | список без значений |
| `POST` | `…/environments/:eid/variables` | `write` | создана с первой версией, `201` |
| `PATCH` | `…/variables/:id` | `write` | правка описания/ключа; поле `value` создаёт версию |
| `DELETE` | `…/variables/:id` | `write` | `204`, версии стёрты |
| `POST` | `…/variables/:id/reveal` | `read` | `{ value, versionNo }` |
| `GET` | `…/variables/:id/versions` | `read` | история без значений: номер, автор, дата |
| `POST` | `…/variables/:id/versions/:no/reveal` | `read` | значение версии |
| `POST` | `…/variables/:id/rollback` | `write` | `{ toVersion }` → новая версия |
| `POST` | `…/environments/:eid/variables/import` | `write` | текст `.env`; создано/обновлено |
| `GET` | `…/environments/:eid/variables/export` | `read` | `text/plain` в формате `.env` |

Импорт — **upsert без удаления**: существующие ключи получают новую версию (если значение изменилось; неизменившиеся не трогаются — иначе каждый импорт плодил бы пустые версии), новые создаются, отсутствующие в файле не удаляются. Удаление — только явное: импорт, стирающий переменные, превращал бы опечатку в файле в потерю секретов.

Маршруты `…/variables/:id` включают и проект, и окружение из адреса; несовпадение любой пары — `404`, как везде.

Разбор и сборка `.env` — отдельная единица `env-format.ts`: строки `KEY=VALUE`, комментарии `#`, пустые строки, одинарные/двойные кавычки при разборе; при сборке значения с переводами строк, `#`, кавычками и пробелами оборачиваются в двойные кавычки с экранированием. Собственные модульные тесты, включая свойство «разбор(сборка(x)) = x».

Контракт — `packages/shared/src/schemas/variable.ts`.

## 7. Интерфейс

Страница `/projects/[id]/variables`: переключатель окружений (из секции «Инфраструктура» — если инфраструктура субъекту недоступна, окружения приходят краткой выборкой прямо из ответа переменных — см. ниже), таблица переменных: ключ, описание, номер версии, дата изменения.

Действия по уровню:

- `read`: кнопка «Раскрыть» у строки — значение подгружается запросом и показывается с кнопками «Скопировать» и «Скрыть»; история версий с раскрытием и выгрузка `.env` с предупреждением «выгрузка фиксируется в журнале»;
- `write`: добавление, правка, удаление с подтверждением, откат из истории, импорт вставкой текста.

Тонкость: страница переменных не должна требовать доступа к секции «Инфраструктура» — уровни выдаются независимо. Поэтому список окружений для переключателя отдаёт сам модуль переменных: `GET /projects/:id/variables/environments` — только `id`, имя и вид, требует уровня `metadata` на секции «Переменные». Это не дыра: состав окружений на уровне метаданных инфраструктуры и так виден, а здесь он служит навигацией к переменным, на которые доступ уже выдан.

Ссылка «Переменные» добавляется в навигацию секций карточки проекта.

Компоненты: `VariableTable` (+ `VariableRow` с раскрытием), `VariableForm`, `VersionHistory`, `EnvImportForm`, `EnvExportPanel`. Хуки: `useQueryVariables`, `useMutationVariable`, `useMutationReveal` и парные к импорту/выгрузке.

## 8. Тестирование

- **Модульные:** `env-format` (разбор, сборка, кавычки, свойство обратимости), схемы контракта (формат ключа), компоненты.
- **Интеграционные (Testcontainers):**
  - репозиторий: права по уровням, версии растут линейно, откат создаёт версию, уникальность ключа, чужое окружение/проект — `404`;
  - **шифрование на месте**: строка в `variable_versions.value_encrypted` начинается с `v1:` и не содержит открытого значения;
  - сервис: раскрытие пишет `variable.revealed`; **ни одна запись журнала не содержит значения**; импорт не создаёт версий для неизменившихся значений;
  - удаление окружения с переменными — `409`.
- **Матрица доступа:** блок переменных — `list: 404/200/200/200`, `reveal: 404/403/200/200`, `create: 404/403/403/201`.
- **HTTP e2e:** CRUD, раскрытие, версии, откат, импорт/выгрузка, коды ошибок.
- **Сквозная (`scripts/e2e.mjs`):** админ создаёт переменную и раскрывает её (журнал получает `variable.revealed`), выгружает `.env`; гость с `metadata` видит ключ и описание, не видит значения, раскрытие — `403`.

## 9. Что этап оставляет следующим

- Этап 8: доступ агентов к списку ключей (профиль по умолчанию) и к значениям (отдельная настройка токена, выключенная по умолчанию — ТЗ 7.3); машинная выгрузка конфигурации при деплое.
- Ротация ключа шифрования — вне этапов, формат `v1:` её допускает.
