# CAIRN — этап 9 «Серверы и карта размещения»: дизайн

Дата: 2026-09-10 · Статус: согласован · Основание: `project-registry-spec [eTsSSz].md`, разделы 3.2 и 6

## 1. Объём

Сервер перестаёт быть набором полей внутри окружения и становится самостоятельной сущностью реестра. Это даёт три вещи, недостижимые при хранении «в строке окружения»:

- **ответ на вопрос «что упадёт, если умрёт эта машина»** — сегодня его приходится собирать глазами, сравнивая IP в карточках разных проектов;
- **срок оплаты машины с предупреждением за две недели** — у сервера, а не у каждого окружения по отдельности;
- **интерактивная карта «серверы → проекты»**, где видно и группировку, и статус.

ТЗ 3.2 перечисляет сервер среди того, что относится к окружению, и не запрещает вынести его в отдельную запись: двухуровневая схема «проект → окружение» сохраняется полностью, сервер подключается к окружению ссылкой. Единица учёта остаётся проектом.

Границы этапа заданы двумя инвариантами ТЗ:

- **модель прав не меняется.** Сервер межпроектен, а выдача — это «субъект × проект × секция». Новый вид выдачи сломал бы закрытый список секций (ТЗ 3), поэтому сервер — административная сущность уровня `users` и журнала: реестр, форма и карта доступны только суперадмину, остальным — `404`;
- **финансы вне объёма (ТЗ 1.4).** Хранится дата «оплачен до» и ничего больше: ни сумм, ни валют, ни истории платежей, ни автопродления.

## 2. Модель данных

**`servers`** — глобальная таблица, вне проектов:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid pk | |
| `name` | text not null, unique | человеческое имя машины (`hetzner-fsn-1`) |
| `owner` | text null | на кого оформлен аккаунт у провайдера и кто платит |
| `host` | text null | доменное имя машины |
| `ip` | text null | |
| `provider` | text null | хостинг |
| `specs` | text null | характеристики |
| `paid_until` | date null | оплачен до, включительно |
| `notes` | text null | |
| `created_at`, `updated_at` | timestamptz not null | |

Имя уникально и обязательно: это единственное поле, по которому машину зовут в разговоре, и два «hetzner» в списке сделали бы карту бесполезной. Всё остальное необязательно — реестр заполняется постепенно, как и окружения.

`paid_until` — календарная дата, а не отметка времени: «оплачен до 12 октября» не имеет часа, и хранение его отметкой времени породило бы вопрос о зоне при сравнении с «сегодня». В контракте — строка `YYYY-MM-DD`.

**`environments`** получает `server_id uuid null references servers(id) on delete restrict`. Ограничение `restrict` повторяет приём, применённый к проектам: сервер нельзя удалить, пока на нём что-то живёт, — удаление должно быть осознанным переносом, а не каскадом.

Из `environments` **удаляются** `ip`, `provider`, `specs`: у машины они одни, и хранение их в каждом окружении неизбежно разошлось бы. Поле **`host` остаётся** — как адрес самого окружения, а не машины: окружение может жить на поддомене или на нестандартном порту, а сервер может быть ещё не заведён. Правило разрешения адреса однозначно и вычисляется в проекции:

> адрес окружения = `environment.host`, если он заполнен; иначе `server.host`.

Два источника истины это не создаёт: поле окружения означает «адрес именно этого окружения», поле сервера — «адрес машины», и приоритет задан явно.

## 3. Права и API

Контроллер `/servers` под `SessionGuard + SuperadminGuard` — тот же приём, что у `/users`. Проверка уровня доступа в репозитории здесь не нужна: у сервера нет проекта, а значит нет и выдачи, которую можно было бы проверить.

| Метод | Что делает |
|---|---|
| `GET /servers` | список: поля сервера, индикатор статуса, число проектов и окружений |
| `GET /servers/:id` | детали, окружения на сервере с именами проектов, статус |
| `POST /servers` | создать |
| `PATCH /servers/:id` | править |
| `DELETE /servers/:id` | `409`, если на сервере есть окружения |
| `GET /servers/map` | данные графа: узлы серверов, узлы проектов, рёбра |

Ответ `GET /servers/map`:

```
{
  servers: [{ id, name, owner, indicator, paidUntil, warnings }],
  projects: [{ id, name, lifecycle, indicator }],
  edges:    [{ serverId, projectId, environments: [{ id, name, kind, health }] }]
}
```

Ребро есть, если хотя бы одно окружение проекта привязано к серверу; окружения перечислены на ребре подписью. Проекты без сервера в граф не попадают — для них есть список проектов на главной.

**Проекция окружения** внутри проекта меняется так: на уровне метаданных сервера не видно вовсе; на уровне чтения возвращается вложенный объект

```
server: { id, name, owner, host, ip, provider, specs } | null
```

Подрядчик с чтением на инфраструктуре видит ровно то же, что видел раньше в полях окружения, плюс владельца машины, и по-прежнему ничего о соседях по серверу: список проектов сервера не входит ни в одну проекцию окружения.

`environmentUpdateSchema` получает `serverId: uuid | null`, `environmentDetailSchema` — вложенный `server`. Токены агентов (MCP) этих данных не получают: профиль токена даёт инфраструктуре уровень метаданных, а на нём сервера в проекции нет вовсе — новых инструментов и новых утечек этап не добавляет.

**Привязка окружения к серверу.** Выпадающий список серверов в форме окружения виден только суперадмину: показать его подрядчику значило бы раскрыть чужую инфраструктуру именами машин. Пользователь с уровнем записи заполняет свободное поле `host` и видит имя уже привязанного сервера как текст; привязку делает суперадмин. Соответственно API отвергает `serverId` в теле запроса от не-суперадмина с `403` — доступ к секции есть, но уровень не позволяет операцию (тот самый случай, когда `403` уместен).

## 4. Миграция существующих данных

Одна SQL-миграция, четыре шага:

1. создать `servers`, добавить `environments.server_id`;
2. вставить по одному серверу на каждую уникальную непустую пару `(host, ip)` из окружений; имя — `host`, иначе `ip`; `provider` и `specs` берутся из самого раннего окружения группы (`created_at`, затем `name` — порядок детерминированный);
3. проставить `server_id`; расхождения `provider`/`specs` внутри группы не теряются, а дописываются в `notes` сервера строками вида «из окружения «Прод»: 4 vCPU, 8 ГБ»;
4. очистить `environments.host` там, где он совпал с `host` созданного сервера (иначе после миграции адрес дублировался бы), и удалить колонки `ip`, `provider`, `specs`.

Отдельная миграция привилегий — `GRANT SELECT, INSERT, UPDATE, DELETE ON servers TO cairn_app`, по образцу `0003_environment_privileges.sql`.

## 5. Статус сервера и предупреждение об оплате

Новых фоновых проверок нет: статус сервера — агрегат уже собираемых health-проверок его окружений плюс срок оплаты. Чистая функция рядом с существующей `indicatorOf`:

```
serverIndicatorOf(environmentStatuses, paidUntil, now)
```

Правила по порядку, порядок и есть приоритет:

1. окружений с health-check нет и `paidUntil` не задан → `unknown`;
2. все окружения с health-check лежат → `down`;
3. часть лежит, либо `paidUntil` ближе `SERVER_WARN_DAYS = 14` дней, либо срок уже прошёл → `warning`;
4. иначе → `ok`.

Просроченная оплата даёт `warning`, а не `down`, намеренно: `down` в CAIRN означает наблюдаемую недоступность, а неоплаченная машина может работать ещё неделю. Смешивать бухгалтерию с наблюдением значит обесценить красный индикатор.

Новый `StatusWarningKind.ServerExpiring` собирается в `warningsOf` рядом с `TlsExpiring` и `DomainExpiring`: `subject` — имя сервера, `detail` — «оплачен до 12.10.2026» либо «оплата истекла 5 дней назад». Предупреждение попадает:

- в статус сервера (реестр и карта);
- в статус каждого проекта, у которого есть окружение на этом сервере, — и, следовательно, поднимает индикатор проекта до «предупреждения» той же машинкой, что и TLS.

Имён чужих проектов в тексте предупреждения нет — только имя машины, которое подрядчику и так видно в карточке его окружения. `StatusRepository` подтягивает серверы через `environments.server_id` тем же запросом, что и окружения проекта.

## 6. Карта

Клиентский компонент `ServerMap`: `<svg>` рисует только рёбра, узлы — слой `<button>` поверх него. Причина такого разделения — доступность и стили: узел-кнопка получает фокус, читается скринридером и оформляется токенами Tailwind, тогда как текст внутри `foreignObject` ни того, ни другого надёжно не даёт.

Раскладка вынесена из React в чистую функцию `layoutServerGraph(servers, projects, edges) → { nodes, edges }`:

- серверы — вертикальной колонкой слева с равным шагом, в порядке имени;
- проекты сервера — веером справа от него;
- проект, висящий на нескольких серверах, ставится по среднему Y своих серверов;
- координаты целочисленные, никакой физики и никакой случайности.

Детерминированность здесь не эстетика, а условие тестируемости: раскладка проверяется unit-тестами без DOM, а компонент — только тем, что отрисовал то, что ему дали.

Интерактив: колесо и кнопки «+/−» — зум, перетаскивание фона — панорама (обе операции меняют один `transform` на обёртке), клик по узлу — подсветка его рёбер и панель деталей на существующем `Drawer`, `Esc` — снять выделение, `Tab` — обход узлов. Библиотека графов не подключается: масштаб — десятки узлов, а `@xyflow/react` принёс бы свой стилевой язык мимо токенов и заглушки `ResizeObserver` в каждый тест.

## 7. Интерфейс

Новые страницы в группе `(app)`, ссылка «Серверы» — в `ADMIN_LINKS`:

- `/servers` — реестр: имя, владелец, провайдер, индикатор, «оплачен до», число проектов; кнопка «Добавить сервер»;
- `/servers/new`, `/servers/[id]/edit` — форма;
- `/servers/map` — карта.

Компоненты, каждый в своей директории, до 100 строк: `ServerList`, `ServerForm`, `ServerCard`, `ServerMap`, `PaidUntilBadge`. Панель деталей узла переиспользует существующий `Drawer`, форма следует `EnvironmentForm`, плашка срока — `StatusIndicator`.

`PaidUntilBadge` выделен отдельно, потому что один и тот же срок показывается в трёх местах (реестр, карта, панель узла), и правило «за сколько дней краснеть» должно жить в одном файле.

## 8. Журнал

Три действия: `server.create`, `server.update`, `server.delete`. Привязка окружения к серверу пишется существующим `environment.update` — это правка окружения, а не сервера. Фоновые проверки статуса в журнал не пишутся, как и раньше.

## 9. Тесты

Сначала падающий тест, затем реализация.

`packages/shared`: схемы сервера — имя обязательно, `paidUntil` в формате даты, `owner` до 200 символов.

`apps/api`: `servers.repository` (не-суперадмину — `404`, удаление занятого сервера — `409`), `servers.service`, `serverIndicatorOf` по всем четырём веткам, `warningsOf` с `ServerExpiring` на границе четырнадцати дней и на просрочке, проекция окружения (сервер отсутствует на уровне метаданных, приходит на уровне чтения), `403` на `serverId` от не-суперадмина, e2e `servers.e2e.test.ts`, интеграционный тест миграции на Testcontainers: вставить окружения со старыми полями, прогнать миграцию, проверить склейку по `(host, ip)` и перенос расхождений в `notes`.

`apps/web`: `ServerForm`, `ServerList`, `PaidUntilBadge`, `ServerMap` (отрисовка и выделение), `layoutServerGraph` (раскладка, проект на двух серверах, пустой граф), плюс дополненные `EnvironmentForm` (селект сервера есть у суперадмина и отсутствует у остальных) и `EnvironmentCard` (сервер и владелец видны, когда пришли в проекции).

## 10. Вне объёма

Осознанно не делаем: географическую карту и тайлы (внешняя зависимость против self-hosted), стоимость, валюту и историю платежей (ТЗ 1.4), автопродление, почтовые уведомления (их нет во всей системе — предупреждения живут в интерфейсе), отдельную TCP-проверку сервера, выдачу прав на серверы, перетаскивание узлов с сохранением позиций.
