# CAIRN — этап 1 «Фундамент»: дизайн

Дата: 2026-08-26 · Статус: согласован · Основание: `project-registry-spec [eTsSSz].md`, раздел 10, пункт 1

## 1. Объём

Реализуется первый этап ТЗ: аутентификация с двухфакторной проверкой, проекты, секция «Инфо», работающая модель выдач доступа, суперадмин, журнал действий.

Модель прав и понятие машинного субъекта проектируются здесь целиком, хотя машинные субъекты появятся только на этапе 8. Причина указана в ТЗ: переделывать модель прав на системе с живыми секретами крайне болезненно.

В объём этапа не входят остальные пять секций проекта, приёмный канал, автопроверки статуса и MCP-доступ.

## 2. Решения по открытым вопросам ТЗ

Раздел 12 ТЗ содержал пять открытых вопросов. На этапе 1 закрыты два.

**Стек и развёртывание.** Монорепо на pnpm workspaces: `apps/web` — Next.js 15 с App Router, `apps/api` — NestJS, `packages/shared` — контракт API. Хранилище — PostgreSQL, доступ через Drizzle. Развёртывание — Docker Compose на собственном сервере: контейнеры web, api, postgres и реверс-прокси с TLS. Ключ шифрования передаётся приложению через переменную окружения и не хранится в базе.

**Многопользовательская работа.** Нужна с первого этапа, включая интерфейс управления доступами. Самостоятельная регистрация отсутствует: пользователи появляются только по приглашению суперадмина.

Три оставшихся вопроса (формат выгрузки конфигурации, публичный статус-экран, глубина хранения версий переменных) относятся к этапам 4 и 6 и здесь не решаются.

## 3. Архитектура

### 3.1 Структура монорепо

```
cairn/
  apps/
    web/          Next.js 15, App Router, RSC + TanStack Query, shadcn/ui, Tailwind
    api/          NestJS, Drizzle, PostgreSQL
  packages/
    shared/       zod-схемы контракта, выведенные из них типы, enum'ы секций и уровней
  docker-compose.yml
```

Выбор в пользу отдельного бэкенда сделан из-за трёх непользовательских потребителей API, которые появятся на следующих этапах: MCP-сервер для агентов, webhook приёмного канала и периодические проверки статуса. Все они обращаются к той же логике прав, что и веб-интерфейс, и должны проходить через один вход.

### 3.2 Контракт API

`packages/shared` — единственный источник типов API. Контракт описывается zod-схемами, типы выводятся из них, фронтенд импортирует те же типы. Swagger генерируется NestJS из этих же схем и служит документацией, а не источником истины.

### 3.3 Связь фронтенда и API

Оба приложения стоят за одним реверс-прокси на одном домене: `/` ведёт на web, `/api` — на api. Браузер обращается к API напрямую, CORS не требуется, сессионная cookie работает как first-party.

Серверные компоненты Next.js обращаются к API по внутреннему адресу контейнера (`http://api:3001`), явно пробрасывая заголовок `Cookie` из входящего запроса через `next/headers`. Публичный адрес используется только браузером. Обёртка над `fetch`, выполняющая этот проброс, — единственный способ обращения к API из серверных компонентов; прямые вызовы `fetch` в компонентах не допускаются, иначе запрос уйдёт без сессии.

## 4. Модель данных

Девять таблиц.

### 4.1 subjects

Единая таблица субъектов доступа: `id`, `kind` (`user` / `agent_token` / `intake_address`), `label`, `created_at`, `revoked_at`.

Выдача доступа всегда ссылается на `subject_id`, а не на пользователя. Это реализует принцип ТЗ «одна модель прав для людей и машин»: когда на этапе 8 появятся токены агентов, а на этапе 3 — приёмные адреса, модель прав менять не придётся. На этапе 1 создаются только субъекты вида `user`.

`revoked_at` — единственный признак активности субъекта во всей системе. Физическое удаление субъектов не предусмотрено ни на этапе 1, ни в дальнейшем: удаление разорвало бы связи в журнале, который обязан оставаться полным. Отзыв субъекта означает, что все проверки прав для него возвращают отказ, а все его сессии немедленно завершаются (см. 4.5).

Внешние ключи на `subjects` объявляются с `ON DELETE RESTRICT`. Каскадного удаления в системе нет нигде.

### 4.2 users

`id`, `subject_id`, `email`, `password_hash`, `totp_secret_encrypted`, `is_totp_enabled`, `is_superadmin`, `created_at`, `updated_at`.

Связь с `subjects` — один к одному. `email` уникален.

Отдельного поля статуса нет намеренно: активность определяется по `subjects.revoked_at`, и второй независимый признак создал бы два источника истины, способных разойтись. Состояние «приглашён, но ещё не вошёл» выводится из `password_hash IS NULL`: до принятия приглашения пароль не задан и вход невозможен.

Пароли хэшируются argon2id. Секрет TOTP шифруется прикладным шифрованием (см. 4.9).

### 4.3 grants

Ядро модели доступа: `id`, `subject_id`, `project_id`, `section`, `level`, `granted_by`, `granted_at`.

Первичный ключ — суррогатный `id`. Уникальный индекс по тройке (`subject_id`, `project_id`, `section`).

`section` — enum из шести значений: `info`, `infrastructure`, `variables`, `docs`, `roadmap`, `chronicle`. Все шесть заводятся сразу, хотя реализована на этапе 1 только `info`. Это позволяет выдавать доступы к будущим секциям без миграции модели.

`level` — enum из трёх значений: `metadata`, `read`, `write`. Уровень «нет» из ТЗ представлен **отсутствием строки**, а не значением enum. Отзыв доступа — удаление строки. Причина: два способа выразить одно и то же состояние («нет строки» и «строка с уровнем none») неизбежно разойдутся в выборках, и часть запросов начнёт отдавать лишнее. Отзыв фиксируется в журнале, поэтому история выдач не теряется при удалении строки.

Кто вправе выдавать и отзывать доступы: на этапе 1 — только суперадмин. Возможность делегировать управление доступами владельцу проекта в объём не входит.

### 4.4 projects

`id`, `slug`, `name`, `purpose`, `stack`, `repo_url`, `owner_user_id`, `lifecycle`, `notes`, `created_at`, `updated_at`.

Эта таблица и есть секция «Инфо»; отдельной таблицы под неё не заводится.

`slug` уникален, генерируется транслитерацией названия при создании, при коллизии дополняется числовым суффиксом; изменить его вручную нельзя, чтобы ссылки не ломались.

`lifecycle` — enum: `development`, `active`, `paused`, `archived`. Задаётся вручную и означает намерение, а не техническую доступность. Технический статус появится на этапе 6.

`owner_user_id` — справочное поле «ответственный» из паспорта проекта (ТЗ 3.1). Прав оно не даёт: чтобы видеть проект, ответственному нужна явная выдача, как и всем остальным. Иначе нарушалось бы требование ТЗ 4.1 «не видит ничего, пока не выдали явно».

Создавать проекты на этапе 1 может только суперадмин.

### 4.5 sessions

`id`, `subject_id`, `token_hash`, `expires_at`, `created_at`, `last_seen_at`, `ip`, `user_agent`, `revoked_at`.

Сессии хранятся в базе ради мгновенного отзыва. Для системы, хранящей секреты, это обязательное свойство: отозвать доступ нужно немедленно, а не по истечении срока токена.

Отзыв субъекта в той же транзакции проставляет `revoked_at` всем его активным сессиям. Отзыв отдельной выдачи сессии не трогает: права проверяются при каждом запросе, поэтому доступ к секции пропадает сразу и без завершения сессии.

Срок жизни сессии — 30 дней с продлением при активности, `last_seen_at` обновляется не чаще раза в минуту, чтобы не писать в базу на каждом запросе.

### 4.6 invitations

`id`, `email`, `subject_id`, `token_hash`, `invited_by`, `expires_at`, `accepted_at`, `created_at`.

Субъект и запись пользователя создаются **в момент приглашения**, а не принятия. Это позволяет суперадмину выдать доступы заранее, чтобы приглашённый увидел свои проекты при первом входе, и делает матрицу доступов полной сразу.

Срок жизни приглашения — 72 часа. Повторное приглашение того же адреса инвалидирует предыдущее (`expires_at` в прошлое) и создаёт новое; пользователь и субъект при этом переиспользуются, выданные доступы сохраняются.

### 4.7 audit_log

`id`, `subject_id`, `subject_kind`, `subject_label`, `action`, `entity_type`, `entity_id`, `project_id`, `metadata` (jsonb), `created_at`.

`subject_kind` и `subject_label` денормализованы намеренно: запись журнала должна оставаться информативной, даже если субъект отозван и его метка позже изменена. Пометка «человек или машина» требуется ТЗ и выводится из `subject_kind`.

Таблица только на добавление. Ограничение обеспечивается на уровне прав PostgreSQL: роль приложения получает `INSERT` и `SELECT`, но не `UPDATE` и не `DELETE`. Запрет в коде недостаточен, потому что журнал — средство расследования инцидентов, включая инциденты с участием самого приложения.

Из этого следует требование к развёртыванию: используются две роли базы данных. Привилегированная роль владеет схемой и применяет миграции Drizzle; ограниченная роль обслуживает приложение и не имеет прав на изменение журнала. Строки подключения для них передаются разными переменными окружения.

### 4.8 totp_challenges

`id`, `user_id`, `token_hash`, `expires_at`, `consumed_at`, `attempts`.

Промежуточное состояние между проверкой пароля и проверкой второго фактора. Срок жизни — 5 минут.

### 4.9 Прикладное шифрование

Отдельной таблицы не требует, но является самостоятельной единицей кода — сервис с двумя методами:

- `encrypt(plaintext: string): string`
- `decrypt(payload: string): string`

Алгоритм — AES-256-GCM. Хранимое значение представляет собой строку из четырёх частей, разделённых двоеточием: версия ключа, nonce, шифротекст, тег аутентификации; три последние — в base64. Пример формы: `v1:<nonce>:<ciphertext>:<tag>`.

Версия ключа в префиксе нужна для ротации: при смене ключа старые значения остаются расшифровываемыми, пока не будут перешифрованы. На этапе 1 ротация не реализуется, но формат её допускает — добавить версию позже, к живым секретам, значит переписать все существующие значения.

Ключ передаётся переменной окружения `CAIRN_ENCRYPTION_KEY` — 32 байта в base64. Приложение отказывается стартовать, если ключ отсутствует или имеет неверную длину: молчаливый запуск без шифрования в системе, хранящей секреты, недопустим.

На этапе 1 сервис применяется только к секретам TOTP. Механизм отрабатывается здесь намеренно, до появления значений переменных на этапе 4.

**Потеря ключа.** Расшифровать существующие значения невозможно — это свойство схемы, а не дефект. На этапе 1 цена потери мала: теряются только секреты TOTP, и суперадмин восстанавливает второй фактор пользователям через CLI (см. 6.6). Процедура: заменить ключ, очистить колонку `totp_secret_encrypted`, снять флаги `is_totp_enabled`, попросить пользователей привязать второй фактор заново. Резервное копирование ключа отдельно от резервных копий базы — требование эксплуатации, фиксируется в документации по развёртыванию.

## 5. Модель доступа

### 5.1 Механизм

Проверка реализуется в прикладном слое: единый сервис, обязательный субъект в сигнатуре репозиториев, выборка строится через соединение с таблицей выдач.

Рассматривались Row-Level Security в PostgreSQL и гибрид. Прикладной слой выбран потому, что уровень «метаданные» по своей природе означает фильтрацию полей, а не строк, и в политиках RLS выражается плохо, а также потому, что три будущих потребителя API проще держать на одной понятной функции проверки, чем на политиках СУБД. Возврат к гибриду возможен на этапе 4, когда появятся настоящие секреты.

### 5.2 Интерфейс проверки

Три метода:

- `resolveLevel(subject, projectId, section)` возвращает уровень доступа или признак его отсутствия. Суперадмин всегда получает `write`, минуя таблицу выдач. Отозванный субъект (`revoked_at` заполнено) всегда получает отсутствие доступа.
- `requireLevel(subject, projectId, section, minimum)` бросает исключение, если уровень ниже требуемого (см. 5.3).
- `visibleProjectIds(subject)` возвращает массив идентификаторов проектов, доступных субъекту хотя бы на уровне `metadata`. Возвращается именно массив, а не подзапрос: сервис прав не должен протекать деталями хранения в вызывающий код и остаётся тестируемым в отрыве от базы. Для масштаба системы (десятки проектов) стоимость такого решения пренебрежима.

### 5.3 Коды ответов и нераскрытие существования

Различаются два случая.

Доступа к секции нет вовсе — возвращается `404 Not Found`. Требование ТЗ: «Секция отсутствует для субъекта, её существование не раскрывается». Ответ `403` сообщил бы, что объект существует, и потому здесь недопустим.

Доступ есть, но его уровень ниже требуемого для операции (например, субъект с `read` пытается изменить проект) — возвращается `403 Forbidden`. Отрицать существование объекта, который субъект только что видел, бессмысленно: это запутывает интерфейс, ничего не скрывая.

Соответственно, недоступные проекты не попадают в списки, а недоступные секции не приходят в карточку проекта.

### 5.4 Встроенность проверки

Репозитории не имеют методов без субъекта в сигнатуре: вызов выглядит как `projectsRepo.findById(subject, id)`, и проверка выполняется внутри. Отдельного вызова проверки, который можно забыть, не существует.

Это выполняет требование ТЗ о проверке на уровне выборки данных, а не в интерфейсе.

### 5.5 Уровень «метаданные»

Реализуется проекциями. Для каждой секции определена функция `project(entity, level)`, возвращающая разный набор полей.

Для секции «Инфо»: на уровне `metadata` — только `name` и `lifecycle`; на уровне `read` — все поля паспорта; на уровне `write` — то же, что `read`, плюс право изменения.

Проекция применяется в сервисном слое до сериализации, поэтому скрытые поля не доходят до контроллера.

## 6. Аутентификация

### 6.1 Вход

Два шага. `POST /auth/login` проверяет email и пароль; если у пользователя включён TOTP, возвращает не сессию, а короткоживущий челлендж. `POST /auth/totp` обменивает челлендж и шестизначный код на сессию.

Разделение на два эндпоинта позволяет считать неудачные попытки второго фактора отдельно от неудачных попыток пароля и не смешивать два разных состояния в одном ответе.

### 6.2 Ограничение попыток

Пароль: 10 неудачных попыток для одного адреса за 15 минут приводят к отказу входа на 15 минут. Счётчик ведётся в памяти приложения — при перезапуске он обнуляется, и это приемлемо: защита рассчитана на автоматический перебор, а не на целенаправленную атаку, от которой защищает второй фактор.

Второй фактор: 5 неудачных попыток кода исчерпывают челлендж — поле `attempts` в `totp_challenges`; челлендж помечается использованным, и вход начинается заново с пароля.

Ответ при неверном пароле и при несуществующем адресе одинаков, чтобы перебором нельзя было выяснить состав пользователей.

Более сложное ограничение частоты запросов (по адресу источника, на прочие эндпоинты) в объём этапа не входит.

### 6.3 Сессия

Cookie с флагами httpOnly, Secure, SameSite=Lax. В cookie — случайный токен, в базе — только его хэш.

### 6.4 Двухфакторная аутентификация

Обязательна для суперадмина, необязательна для остальных пользователей. Пока суперадмин не привязал TOTP, ему доступен единственный экран — настройка второго фактора.

### 6.5 Первый суперадмин

Создаётся CLI-командой при развёртывании: `pnpm --filter api cli create-superadmin`.

Через веб-интерфейс первый администратор не создаётся: открытый эндпоинт создания администратора, нужный ровно один раз, остался бы в системе навсегда как постоянная уязвимость.

### 6.6 Восстановление доступа суперадмина

Сброс второго фактора обычному пользователю выполняет суперадмин через интерфейс. Для самого суперадмина этого недостаточно: при единственном администраторе потеря устройства с TOTP делает систему недоступной навсегда.

Поэтому предусмотрена CLI-команда `pnpm --filter api cli reset-totp <email>`, снимающая привязку второго фактора. Она требует доступа к серверу, то есть уже предполагает владение машиной, и потому не ослабляет модель безопасности. Каждый её вызов пишется в журнал.

Резервные коды восстановления в объём этапа 1 не входят: CLI решает ту же задачу без дополнительной сущности в модели данных.

### 6.7 Приглашения

Суперадмин заводит пользователя, система выдаёт одноразовую ссылку с ограниченным сроком действия. Принявший приглашение задаёт пароль и, при желании, привязывает TOTP.

Отправка почты на этапе 1 не реализуется: ссылка показывается суперадмину для передачи любым способом. Это снимает зависимость от SMTP до этапа 3, где почта появится для приёмного канала.

## 7. Журнал действий

### 7.1 Точка записи

Журналирование выполняется на уровне сервисов, а не контроллеров. Причина: на будущих этапах те же сервисы будут вызываться из MCP-сервера и обработчика webhook, и журналирование должно работать для них без дополнительного кода.

### 7.2 Что фиксируется на этапе 1

Вход, выход, неудачная попытка входа по паролю, неудачная попытка второго фактора, исчерпание челленджа; создание и изменение проекта; выдача, изменение и отзыв доступа; создание, повторная выдача и принятие приглашения; отзыв и восстановление субъекта; привязка и сброс второго фактора, включая сброс через CLI.

### 7.3 Транзакционность

Запись в журнал выполняется в той же транзакции, что и само действие. Либо есть и изменение, и его след, либо нет ни того ни другого. Журнал, из которого могут пропадать записи об успешных действиях, не выполняет свою функцию.

Исключение — события неудачного входа: они не сопровождаются изменением данных и пишутся отдельной транзакцией.

## 8. API

Список эндпоинтов этапа 1. Он же определяет объём набора тестов из раздела 9.3.

**Аутентификация:** `POST /auth/login`, `POST /auth/totp`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/totp/setup`, `POST /auth/totp/confirm`.

**Приглашения:** `POST /invitations` (создать), `GET /invitations/:token` (проверить действительность), `POST /invitations/:token/accept` (задать пароль и войти).

**Проекты:** `GET /projects` (список видимых), `POST /projects` (создать), `GET /projects/:id` (карточка с перечнем доступных секций), `PATCH /projects/:id` (правка полей «Инфо»).

**Доступы:** `GET /projects/:id/grants` (матрица по проекту), `PUT /projects/:id/grants` (установить уровень для пары «субъект × секция»), `DELETE /projects/:id/grants/:grantId` (отозвать).

**Пользователи:** `GET /users`, `POST /users/:id/revoke`, `POST /users/:id/restore`, `POST /users/:id/reset-totp`.

**Журнал:** `GET /audit` с фильтрами по субъекту, проекту, типу действия и диапазону дат.

Эндпоинты проектов и доступов проверяют права через сервис из раздела 5; эндпоинты пользователей, приглашений и журнала доступны только суперадмину.

## 9. Интерфейс

Язык интерфейса — русский, без библиотеки локализации.

### 9.1 Экраны

**Вход** — форма пароля, форма второго фактора, экран принятия приглашения.

**Сводка.** Карточки доступных проектов с состоянием жизненного цикла. Место под индикаторы технического статуса закладывается, сами индикаторы появятся на этапе 6.

**Карточка проекта.** На этапе 1 содержит одну секцию — «Инфо». Секции рендерятся по списку, пришедшему от API: недоступные секции не приходят и потому физически отсутствуют в разметке. Требование ТЗ — недоступные секции отсутствуют, а не показываются заблокированными.

**Создание и правка проекта.** Форма полей паспорта. Доступна суперадмину (создание) и субъектам с уровнем `write` на секции «Инфо» (правка).

**Управление доступами.** Матрица «субъект × секция» для проекта, в ячейках — выбор уровня либо его отсутствие. Все шесть секций отображаются сразу: выдать доступ к документации можно и до того, как секция реализована.

**Журнал действий.** Фильтры по субъекту, проекту и типу действия. Только чтение, без возможности правки из интерфейса.

**Пользователи.** Список, приглашение, отзыв и восстановление доступа, сброс второго фактора.

### 9.2 Правила фронтенда

Компоненты до 100 строк, каждый в своей директории с `index.ts`. Пропсы — интерфейс `IProps` в `types.ts`; при отсутствии пропсов файл не создаётся. Массивы и объекты для JSX выносятся в `constants.ts`. Серверные компоненты по умолчанию, `use client` только для форм и интерактивных элементов. Асинхронные операции — через TanStack Query с префиксами `useQuery`/`useMutation` в именах хуков.

Доступность: семантическая разметка, aria-подписи для интерактивных элементов без видимого текста, клавиатурная навигация, контраст по WCAG AA. Компоненты shadcn/ui на Radix дают базовое поведение из коробки.

## 10. Тестирование

Разработка ведётся по TDD: для каждой единицы работы сначала пишется падающий тест, затем реализация.

### 10.1 Инструменты

Vitest в обоих приложениях, React Testing Library для компонентов, Testcontainers для интеграционных тестов на настоящем PostgreSQL.

### 10.2 Уровни

**Юнит-тесты** — чистая логика: `resolveLevel` для всех сочетаний уровней и ролей, проекции полей, шифрование и расшифровка, отказ старта при неверном ключе, хэширование паролей, генерация и проверка TOTP, счётчики попыток.

**Интеграционные тесты** — репозитории на реальной базе, транзакционность журнала, невозможность изменить журнал ограниченной ролью базы, отзыв субъекта с завершением сессий, повторное приглашение.

**Тесты компонентов** — React Testing Library, файлы вида `ComponentName.test.tsx`.

### 10.3 Матрица доступа как тесты

Отдельный набор тестов проверяет для каждой пары «уровень доступа × эндпоинт» из раздела 8, что субъект получает ожидаемый ответ: `404` при отсутствии доступа, `403` при недостаточном уровне, корректную проекцию полей при достаточном.

Этот набор — исполняемая версия таблицы из раздела 4.3 ТЗ. Он растёт вместе с каждой новой секцией на последующих этапах и служит защитой от регрессий в модели доступа.

## 11. Вне объёма этапа 1

Восстановление пароля по почте (до появления SMTP на этапе 3 сброс выполняет суперадмин), ограничение частоты запросов сверх описанного в 6.2, ротация ключа шифрования, резервные коды восстановления, делегирование управления доступами владельцу проекта, темы оформления, мобильная адаптация сверх той, что даёт Tailwind по умолчанию.

## 12. Порядок реализации

Этап разбивается на четыре фазы, каждая с проверяемым результатом.

1. **Основание.** Монорепо, контракт в `packages/shared`, схема базы, миграции, Docker Compose, две роли базы, сервис шифрования. Результат: база поднимается, шифрование покрыто тестами.
2. **Права и данные.** Сервис проверки прав, репозитории проектов и выдач, проекции, журнал. Результат: матрица доступа из раздела 10.3 проходит на уровне сервисов.
3. **Аутентификация.** Пароли, TOTP, сессии, приглашения, CLI-команды. Результат: вход с двумя факторами работает, отзыв немедленный.
4. **Интерфейс.** Экраны из раздела 9.1. Результат: система пригодна к использованию.

## 13. Что этап 1 оставляет следующим

Модель субъектов вмещает машинные субъекты без изменений схемы. Enum секций содержит все шесть значений. Прикладное шифрование с версионированием ключа отрабатывается на секрете TOTP до появления значений переменных. Журналирование на уровне сервисов работает для будущих непользовательских потребителей API без дополнительного кода. Карточка проекта рендерит секции по данным от API, поэтому добавление секции не требует правки логики отображения.

Отдельно фиксируется на будущее: требование ТЗ 7.3 «доступ к значениям переменных — отдельная явная настройка токена» отображается в существующую модель уровней как `variables: read` против `variables: metadata`. Заводить для этого отдельный флаг вне модели уровней не следует — это раздвоило бы модель прав, чего ТЗ прямо избегает.
