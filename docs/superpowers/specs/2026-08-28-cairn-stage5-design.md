# CAIRN — этап 5 «Роадмап»: дизайн

Дата: 2026-08-28 · Статус: согласован · Основание: `project-registry-spec [eTsSSz].md`, раздел 10, пункт 5

## 1. Объём

Реализуется секция «Роадмап» (ТЗ 3.5): последовательность версий с чекпоинтами, вычисляемый прогресс, диаграмма-таймлайн и единственная в системе публичная ссылка. Плюс минимальное «поднять запись хроники в чекпоинт» (ТЗ 3.6) — приёмник появляется именно здесь.

Сознательные ограничения ТЗ соблюдаются буквально: у чекпоинта нет исполнителей, оценок, дат, комментариев и вложенности — таких полей не появится ни в схеме, ни в контракте (ТЗ 1.4: условие жизнеспособности продукта).

Вне объёма: второй открытый вопрос ТЗ («нужен ли публичный статус-экран помимо роадмапа») не решается — публичной остаётся только страница роадмапа.

## 2. Модель данных

### 2.1 roadmap_versions

`id`, `project_id`, `label`, `planned_date`, `state`, `position`, `created_at`, `updated_at`.

`project_id` — `ON DELETE RESTRICT`, как везде. `label` — обозначение («v1.2.3», «Осень»), уникально в проекте: две версии с одним именем — путаница в диаграмме. `planned_date` необязательна (тип `date`). `state` — enum `planned` / `in_progress` / `released`, задаётся вручную: состояние версии — намерение, как жизненный цикл проекта.

`position` — место в последовательности: при создании `max + 1`, правится через PATCH. Порядок версий значим («последовательность версий», ТЗ 3.5) и не выводим из обозначений: сортировать «v2» и «Осень» лексикографически бессмысленно.

### 2.2 roadmap_checkpoints

`id`, `version_id` (restrict), `title`, `is_done`, `position`, `created_at`, `updated_at`.

Состав закрыт: формулировка результата и признак «закрыт». Порядок — `position`, как у версий.

### 2.3 Вычисляемое

**Прогресс версии** — доля закрытых чекпоинтов, считается в выборке (`done/total`); версия без чекпоинтов имеет прогресс 0/0 и рисуется пустой отметкой. **Стадия проекта** — позиция текущей версии: первая `in_progress` по порядку, иначе первая `planned`; если все выпущены — последняя. Ни то, ни другое не хранится (ТЗ 3.5: «прогресс не хранится, а вычисляется») — хранение неизбежно разошлось бы с чекпоинтами.

### 2.4 roadmap_public_links

`id`, `project_id` (unique, restrict), `token` (unique), `created_at`.

Публикация включена = строка существует; выключена = строки нет — тот же принцип, что у выдач: два способа записать одно состояние разошлись бы в выборках. Токен — `generateToken` (32 байта base64url), хранится открыто: его показывают и рассылают. Перевыпуск = отключить + включить; старая ссылка гаснет явно.

## 3. Доступ

Секция `Section.Roadmap` (ТЗ 4.3, строка «Роадмап»):

| Уровень | Доступно |
|---|---|
| нет строки выдачи | `404` |
| `metadata` | версии: обозначение, состояние, дата, позиция, прогресс (числа) — **без формулировок чекпоинтов** |
| `read` | плюс формулировки чекпоинтов; просмотр публичной ссылки |
| `write` | правка версий и чекпоинтов |

Проекция версии через `projectByLevel`: метаданные — паспорт версии и `progress: { done, total }`; подробность — массив чекпоинтов. Управление публичной ссылкой — суперадмин: раскрытие данных наружу — решение администратора, как приёмный адрес.

## 4. Публичный доступ

`GET /api/public/roadmap/:token` — без сессии. Ответ: название проекта, стадия, версии с чекпоинтами и прогрессом — то же, что видит уровень `read` внутри. Мусорный токен и отключённая публикация — одинаковый `404`.

Страница `/roadmap/[token]` — серверная, в отдельной группе маршрутов без навигации приложения: заголовок с названием проекта, диаграмма, список версий с чекпоинтами. Только чтение, никаких ссылок внутрь системы.

Включение ссылки — осознанное раскрытие формулировок всем, у кого есть ссылка; это проговаривается в интерфейсе при включении.

## 5. API

| Метод | Маршрут | Право |
|---|---|---|
| `GET` | `/projects/:id/roadmap` | `metadata` — весь роадмап в проекции по уровню + стадия |
| `POST` | `/projects/:id/roadmap/versions` | `write` |
| `PATCH` / `DELETE` | `/projects/:id/roadmap/versions/:vid` | `write`; удаление версии удаляет её чекпоинты явной строкой |
| `POST` | `/projects/:id/roadmap/versions/:vid/checkpoints` | `write` |
| `PATCH` / `DELETE` | `/projects/:id/roadmap/versions/:vid/checkpoints/:cid` | `write` |
| `GET` | `/projects/:id/roadmap/public-link` | `read`; `404`, если не опубликовано |
| `POST` / `DELETE` | `/projects/:id/roadmap/public-link` | суперадмин; повторное включение — `409` |
| `GET` | `/public/roadmap/:token` | сам токен |

Принадлежность «проект → версия → чекпоинт» сверяется в запросах; чужое — `404`.

Журнал: `roadmap_version.created/updated/deleted`, `checkpoint.created/updated/deleted`, `roadmap.published`, `roadmap.unpublished`. Формулировки в журнал попадают (в отличие от значений переменных они не секрет), удаление версии пишет её обозначение.

Контракт — `packages/shared/src/schemas/roadmap.ts`; `RoadmapVersionState` — в `enums.ts`.

## 6. Диаграмма

`RoadmapTimeline` — SVG: горизонтальная линия, версии — отметки по порядку `position`. Заполненность отметки равна прогрессу: сектор-«пирог» (арк от 12 часов по часовой), выпущенная версия — полный круг независимо от чекпоинтов (выпущена — значит завершена), текущая — выделена внешним кольцом. Подписи-обозначения под отметками. Требование ТЗ «стадия читается за две секунды» проверяется составом: закрашенные слева, пустые справа, кольцо на текущей.

Компонент чистый (данные пропсами), тестируется по разметке: доля сектора, полный круг у `released`, кольцо у текущей.

## 7. Интерфейс

**Страница секции** `/projects/[id]/roadmap`: диаграмма сверху, ниже — версии по порядку (обозначение, состояние, дата, прогресс; чекпоинты списком с галочками при `read+`); при `write` — добавление/правка/удаление версий и чекпоинтов, переключение `is_done` галочкой; суперадмину — блок публичной ссылки (включить с предупреждением, скопировать, отключить с подтверждением). Ссылка «Роадмап» — в навигацию секций карточки.

**Из хроники**: у записи — кнопка «В чекпоинт» при `write` на роадмапе (уровень уже приходит в `useQuerySections`); на месте разворачивается выбор версии и поле формулировки, предзаполненное заголовком записи. Отправка — обычный `POST` чекпоинта; связи между секциями не создаётся.

Компоненты: `RoadmapTimeline`, `VersionCard` (+ `CheckpointList`), `VersionForm`, `CheckpointForm`, `PublicLinkPanel`, `PromoteToCheckpoint` (в хронике). Хуки: `useQueryRoadmap`, мутации версий/чекпоинтов, `useQueryPublicLink` + мутации, публичная страница ходит серверным fetch без cookie.

## 8. Тестирование

- **Модульные:** схемы контракта, проекция версии, `RoadmapTimeline` (доля сектора, released = полный, кольцо текущей), компоненты и формы.
- **Интеграционные:** репозиторий — права, прогресс, стадия (первая `in_progress`, иначе первая `planned`, все выпущены — последняя), позиции, уникальность обозначения, чужой проект/версия; сервис — журнал всех действий, отказ не оставляет следов.
- **Матрица доступа:** блок роадмапа — `list: 404/200/200/200`, формулировки чекпоинтов скрыты на `metadata`, `create: 404/403/403/201`.
- **HTTP e2e:** CRUD версий и чекпоинтов, публичный маршрут (валидный токен без сессии; мусорный, после отключения — `404`; повторная публикация — `409`).
- **Сквозная (`scripts/e2e.mjs`):** версия с чекпоинтами → один закрыт → публикация → чтение публичной страницы агентом без cookie (формулировки видны) → отключение → `404`; гость с `metadata` видит прогресс `1/2`, но не формулировки.
