# CAIRN

Единый реестр независимых проектов: где проект развёрнут, жив ли он, чем настроен,
что по нему решали и на какой стадии находится.

Реализованы этапы 1–10: аутентификация с двухфакторной проверкой, проекты
со всеми шестью секциями — «Инфо», «Инфраструктура», «Переменные»,
«Документация», «Роадмап», «Хроника» — модель выдач доступа, журнал
действий, автопроверки статуса.

Документация — Markdown-страницы «как это устроено сейчас» с безопасным
собственным рендером (HTML в тексте остаётся текстом); запись хроники
поднимается в чекпоинт роадмапа или страницу документации одним действием.

Серверы вынесены в отдельный реестр: машина заводится один раз, окружения
разных проектов на неё ссылаются, а экран «Серверы» показывает владельца,
статус и срок оплаты и предупреждает за две недели до его окончания.
Карта размещения `/servers/map` рисует граф «серверы → проекты»: видно,
что упадёт вместе с конкретной машиной. Реестр и карта доступны только
суперадмину — список машин межпроектен; подрядчик видит имя и параметры
лишь той машины, на которой стоит его окружение.

Домены ведутся тем же способом, что и серверы, но с одной поблажкой: корень
(`example.com`) появляется в реестре сам, как только подрядчик вписал адрес
стенда — ради адреса не нужно дёргать владельца реестра. Владельца,
регистратора и срок продления задаёт суперадмин на экране «Домены»;
предупреждение приходит за месяц, а не за две недели, потому что
освободившийся домен могут перехватить в тот же день. Карта `/domains/map`
показывает, какие проекты держатся на каком корне.

Статус проектов обновляется сам: система опрашивает health-check адреса
окружений, следит за сроками TLS-сертификатов и регистрации доменов
(интервал — `CAIRN_STATUS_CHECK_INTERVAL_MINUTES`, по умолчанию 15 минут,
`0` — выключено), а сводка показывает индикаторы и предупреждения о сроках.
Первый прогон идёт при подъёме приложения, а не через интервал: иначе
после каждого деплоя статус устаревал на четверть часа. Два прогона
одновременно не идут — ни в одном процессе, ни в двух: замок лежит в базе
(`pg_try_advisory_xact_lock`). Кнопка «Проверить сейчас» отвечает `202` и
оставляет обход в фоне; поверх идущего прогона второй не начинается.
Руками задаётся только «приостановлен» — через жизненный цикл проекта.
Архивный проект не проверяется вовсе: чинить его никто не собирается.

Пока падение открыто, его адреса переспрашиваются отдельно и часто —
`CAIRN_STATUS_DOWN_POLL_SECONDS`, по умолчанию раз в минуту, `0` — только
сводный прогон. Без этого шага длительность падения была известна лишь с
точностью до интервала обхода: в истории любой отрезок оказывался кратен
четверти часа. Опрашиваются только лежащие адреса и только health —
живых и сроков этот шаг не трогает, а идущему прогону не мешает (замок у
них общий, и совпавший шаг просто пропускается).

В момент рождения инцидента снимается слепок: куда смотрело имя и что
ответили порты `443` и `80` машины, на которую оно смотрело. Он отвечает
на единственный вопрос, на который не отвечает причина падения, — к кому
идти: отказ на порту означает, что путь до машины цел и не слушает служба
(это к нам), живой `80` при мёртвом `443` — фильтр по порту (это к
провайдеру или хостеру), молчание обоих — оборванный путь, а
неразрешённое имя переводит разговор на DNS, до машины дело не дошло.
Слепок снимается один раз за падение и только у тех адресов, которым
инцидент вот-вот откроют: у приостановленного проекта и при собственной
слепоте его нет. Предел ожидания пробы порта —
`CAIRN_PORT_PROBE_TIMEOUT_SECONDS`, по умолчанию 3 секунды. Проба врёт на
машине за туннелем или прокси — такой клиент принимает соединение за любой
адрес сам; в контейнере развёртывания туннеля нет, а вердикт о падении
по-прежнему за HTTP-проверкой, соврать которой туннель не может.

Время, за которое система не наблюдала ничего, считается отдельно от
падений. Пустой журнал инцидентов означает и «адрес отвечал», и «никто не
спрашивал», а доля времени считалась как первое: три часа неработавшего
API выглядели в истории тремя часами исправной работы — аптайм врал в плюс
ровно тогда, когда проверок не было. Теперь прогон записывает пропуск
наблюдения (тишина дольше двух интервалов обхода либо собственная слепота
из абзаца ниже), а доля в разборе адреса считается от наблюдавшегося
времени; сколько его не было, названо там же отдельной строкой. Своей
переменной у этого нет: порог берётся из интервала обхода, а с выключенным
циклом регулярного наблюдения никто не обещал — пропуски тогда не пишутся
вовсе.

«Упал проект» отличается от «сеть потеряна у нас» по контрольным адресам
(`CAIRN_STATUS_CONTROL_URLS`): проверки идут из контейнера, и собственная
потеря сети выглядит как падение всех проектов разом — пуши о каждом из
них и ложны, и приходят пачкой. Контрольные адреса спрашиваются только в
момент падения, до первого ответившего, пустым `GET` без содержимого
проектов; если не ответил никто, прогон не сводит инциденты вовсе — ни
открытия, ни закрытия, — но записи проверок остаются, и на экране адрес
красный с той причиной, которую правда увидели. Пустое значение выключает
проверку; в закрытом контуре назовите вместо внешних адрес, достижимый
оттуда, — иначе «сеть потеряна» станет вечным вердиктом.

Из «Инфраструктуры» проекта открывается отдельный экран «Статус»
(`/projects/:id/infrastructure/status`) с теми же правами доступа: карточки
адресов, фильтры и графики зарегистрированных падений за 7, 30 или 90 дней.
Во время прогона показывается индикатор ожидания до освобождения блокировки
в базе, в том числе после перезагрузки страницы. До первого результата адрес
ожидает проверки; пустой журнал инцидентов не считается измеренным аптаймом.

Срок регистрации запрашивается напрямую в RDAP-реестре из списка IANA.
Не все зоны публикуют эти данные: отсутствие источника или отказ реестра
показывается отдельно от доступности сайта. Успешный ответ кэшируется на
`CAIRN_RDAP_CACHE_HOURS`, отказ — не более пяти минут. В реестре доменов
неизвестный срок продления означает незаполненную дату оплаты, а не отсутствие
проверок сайта; дату можно указать вручную в карточке корневого домена.

Пределы ожидания проверок, число попыток DNS и срок жизни кэша ответов
реестра настраиваются — все переменные перечислены в `.env.example`
разделом «Автопроверки статуса» и прокинуты в службу `api`.

Предупреждения реестров — срок оплаты машины, срок продления корня,
расхождение привязки — индикатор проекта не красят и приходят отдельным
списком только суперадмину: отвечать на них проекту нечем, межпроектную
машину и корневой домен правит он один.

Падение адреса не только красит индикатор, но и становится инцидентом:
упавший адрес переспрашивается через `CAIRN_HEALTH_RECHECK_DELAY_SECONDS`
(по умолчанию 30 секунд; `0` — переспросить сразу, без паузы), и только
подтверждённый отказ открывает инцидент. У адреса видно, с каких пор он
лежит и сколько раз падал, а открытие и закрытие инцидента уходят
веб-пушем тем, кто подписался на уведомления кнопкой на сводке, — в
пределах своих прав на секцию «Инфраструктура». Больше трёх событий
одного вида в прогоне сводятся в одно уведомление: упавшая машина роняет
все свои адреса сразу.

Уведомления требуют трёх переменных — `CAIRN_VAPID_PUBLIC_KEY`,
`CAIRN_VAPID_PRIVATE_KEY`, `CAIRN_VAPID_SUBJECT` (вида `mailto:`). Пара
генерируется командой `pnpm --filter @cairn/api cli generate-vapid-keys`;
приватный ключ — секрет и живёт вне базы, рядом с ключом шифрования. Без
всех трёх уведомления выключены целиком, и кнопка подписки не
показывается. Доставку ретранслирует push-служба браузера: она видит
факт отправки, но не содержимое — полезная нагрузка шифруется ключами
получателя.

Саммари созвона разбирается на задачи: текст вставляется или загружается
файлом (`.txt`, `.md` в UTF-8) на вкладке «Саммари», ложится в «Хронику»
проекта записью с источником «Саммари созвона», модель предлагает разбивку
на задачи, человек правит её в черновике и одной кнопкой превращает в
версию роадмапа с чекпоинтами. Предложенные строки помечены «предложено
моделью» — применяется только то, что человек подтвердил; порядок меняется
кнопками «Выше»/«Ниже», доступными с клавиатуры. Правка текста после
разбивки помечает задачи возможно устаревшими, но релиз не блокирует:
судит человек, он видит на одном экране и текст, и задачи. Текст можно не
набирать вовсе, а получить расшифровкой загруженной записи созвона — своим
разделом ниже.

Разбивка настраивается **с экрана** «Настройки» (`/settings`, блок «Службы
модели»; ссылка в полосе навигации справа, рядом с именем, и только у
суперадмина) или переменными окружения — и порядок между ними жёсткий:

- **главный путь — экран.** Суперадмин правит адрес службы, схему
  авторизации, ключ, модель, каталог, вид узла, предел ожидания и
  выключатель, и правка действует **сразу, без перезапуска API**. Там же
  кнопка «Проверить связь»: она делает один живой вызов и называет, что
  делать по исходу («ключ не принят», «в адресе лишний или недостающий
  `/v1`», «неверное имя модели»). Вызов платный, поэтому сам он не
  запускается никогда — ни при сохранении, ни при подъёме, ни по
  расписанию, — а наружу отправляет фразу-константу из нашего исходника,
  а не данные проекта;
- **запасной путь — `.env` и перезапуск.** Он действует, **пока в базе нет
  записи** настройки. Установки, собранные по прежнему README, продолжают
  работать без единой правки: переноса настройки из окружения в базу не
  делается намеренно.

> **Вписали ключ в `.env`, перезапустили — и ничего не изменилось.** Это
> значит, что настройка задана в интерфейсе: база главнее окружения, и
> источник выбирается целиком на узел, а не по полю. Ответ — бирка в
> карточке узла: «Задано в интерфейсе» против «Из окружения». Имён
> переменных экран не называет: бирка уже сказала всё, что нужно, а список
> из семи имён отвечал повторно. Чинится кнопкой «Вернуть настройку
> окружения» — она удаляет запись, и вписанное в `.env` начинает
> действовать немедленно, тоже без перезапуска.

Что ещё стоит знать про ключ службы:

- **он шифруется тем же `CAIRN_ENCRYPTION_KEY`**, что значения переменных
  проекта, и в резервную копию базы этот ключ не входит
  (`scripts/backup.sh`). Восстановление на машине с другим ключом даёт
  узел с нерасшифровываемым ключом — экран скажет это словами и предложит
  вписать ключ заново или сбросить настройку к окружению;
- **версий ключа нет**: сменили — старый у провайдера не вернуть. Откат
  настройки тоже отсутствует, есть только сброс к окружению;
- **наружу ключ не выходит никуда**: ни в ответ ручки, ни в журнал, ни в
  текст отказа, ни в лог. На экране о нём сказано ровно «задан» или «не
  задан», а поле ввода — только на запись: пустым его оставляют, чтобы не
  менять.

Каждая правка попадает в журнал, и смена ключа — **своим** действием
(«Изменён ключ службы модели») отдельно от смены адреса и модели.

Семь переменных узла остаются **запасным источником**, и вот они все до
одной (`CAIRN_TASK_SUGGESTER_MAX_CHARS` и `_MAX_TASKS` — наоборот,
единственный источник: это настройка нашего поведения, а не провайдера):

- `CAIRN_TASK_SUGGESTER` — вид адаптера: `external` (внешний
  OpenAI-совместимый API), `local` (свой endpoint в контуре) или `off`,
  который выключает порт целиком при любом ключе;
- `CAIRN_TASK_SUGGESTER_BASE_URL` — адрес OpenAI-совместимого API. Пустое
  значение при `local` означает «выключено», а не «подставить внешний»:
  подстановка отправила бы текст локальной установки наружу;
- `CAIRN_TASK_SUGGESTER_AUTH_SCHEME` — как ключ предъявляется службе:
  `bearer` (`Authorization: Bearer …` — OpenAI, ProxyAPI), `api_key`
  (`Authorization: Api-Key …` — Yandex) или `none` (заголовка нет вовсе).
  Умолчание — `bearer`, мусор читается как оно же. **Несовместимость,
  названная прямо:** установка с `CAIRN_TASK_SUGGESTER=local` и без ключа
  обязана дописать `CAIRN_TASK_SUGGESTER_AUTH_SCHEME=none`, иначе узел
  окажется ненастроенным — ключ теперь требуется при любой схеме, кроме
  `none`;
- `CAIRN_TASK_SUGGESTER_FOLDER` — каталог провайдера: нужен службам
  Yandex. OpenAI-совместимому узлу Yandex каталог задаётся внутри имени
  модели (`gpt://<каталог>/…`), и этот адаптер заголовка с каталогом не
  отправляет;
- `CAIRN_TASK_SUGGESTER_API_KEY` — ключ. Пустой при `external` тоже
  выключает порт: **на свежей установке текст наружу не уходит**, пока
  ключ не вписали руками. При `local` ключ не нужен, и этот путь
  закрывает утечку целиком;
- `CAIRN_TASK_SUGGESTER_MODEL` — модель (умолчание `gpt-4o-mini`):
  настройкой, а не кодом;
- `CAIRN_TASK_SUGGESTER_TIMEOUT_SECONDS` — сколько ждать ответа
  (умолчание `60`). Повторов порт не делает: повтор — это нажатие
  человека, а автоповтор на платном API удвоил бы счёт молча;
- `CAIRN_TASK_SUGGESTER_MAX_CHARS` — предел объёма текста, уходящего
  наружу (умолчание `262144` — предел самого текста саммари, то есть
  четыре часа созвона). Длиннее не отправляется вовсе: отказ
  приходит до сети и называет это число;
- `CAIRN_TASK_SUGGESTER_MAX_TASKS` — сколько задач принимаем от модели
  (умолчание `50`). Предел формы выше (200): человек вправе дописать
  больше, чем предложила машина.

Мусор и неположительное значение в числовых переменных означают
умолчание, а не «ждать вечно».

**Без настройки поток работает полностью**: кнопка «Создать задачи на
основе текста» выключена с объяснением, а задачи набираются руками и
превращаются в релиз так же. Текст саммари уходит на настроенный адрес, и
об этом постоянной подписью сказано над самой кнопкой: какой узел, какая
модель. Это одно из **трёх** мест, где наружу уходит **содержимое** проекта
(два других — расшифровка записи созвона и выгрузка задач в трекер, оба
своими разделами ниже): RDAP-запрос называет
реестру только доменное имя, а веб-пуш шифруется ключами получателя. Вместе с текстом не уходит ничего больше — ни имена
проектов и окружений, ни адреса, ни переменные, ни имя пользователя. Запись о передаче попадает в журнал
**до** обращения к модели — нет записи, нет и передачи. CAIRN при этом не
обещает, что провайдер не хранит присланное: это предмет договора с
провайдером, а не свойство нашего кода.

Роадмап — последовательность версий с чекпоинтами: прогресс вычисляется,
диаграмма показывает стадию за две секунды, а суперадмин может опубликовать
роадмап наружу по ссылке `/roadmap/<токен>` — единственная публичная
страница системы; отключение ссылки гасит её немедленно. Запись хроники
поднимается в чекпоинт одним действием. Формулировка живёт у **задачи**
проекта, а чекпоинт — это её размещение в версии: подробности в разделе
«Выгрузка задач в трекер» ниже.

Переменные — самая чувствительная секция: значения шифруются ключом
`CAIRN_ENCRYPTION_KEY`, живущим вне базы; каждое изменение создаёт новую
версию с возможностью отката; значение никогда не попадает в списки и
раскрывается только отдельным действием с записью в журнал; `.env`
импортируется и выгружается одним действием (выгрузка тоже фиксируется
в журнале). Уровень «метаданные» показывает, какие переменные нужны
проекту, не показывая их значений.

У проекта есть уникальный приёмный адрес: внешний инструмент отправляет
сводку POST-запросом (JSON с полем `content` или чистый текст) — и она
появляется в хронике с пометкой источника. Адрес создаёт и отзывает
суперадмин на странице хроники; приём почты на тот же адрес появится позже.
Автопроверки статуса окружений — этап 6.

## Расшифровка записи созвона

Текст саммари можно не набирать, а получить из записи: на вкладке «Саммари»
загружается файл созвона — видео (MP4, MOV, MKV, WEBM) или аудио (MP3, M4A,
WAV, OGG, FLAC), — из него извлекается звуковая дорожка, дорожка уходит
службе распознавания, а полученный текст ложится записью «Хроники» и дальше
идёт обычным путём «текст → задачи → релиз». Текст правится как любой другой
текст саммари: расшифровка, которую нельзя поправить, была бы хуже вставленной
руками. Пока расшифровка идёт, на экране видна очередь с состоянием; готовую
дорожку можно переслушать, а расшифровку — запустить снова (она затрёт
правки, поэтому спрашивает подтверждение).

**Наружу уходит звуковая дорожка созвона целиком** — со всем сказанным,
включая то, чего в тексте саммари потом не будет. **Видео наружу не уходит**:
из файла берётся только звук, кадры не разбираются, не хранятся и не
показываются. Это второе из трёх мест, где содержимое проекта покидает машину
(третье — выгрузка задач в трекер, своим разделом ниже); запись о передаче
попадает в журнал **до** первого байта — нет
записи, нет и передачи. Заголовок логирования данных не отправляется никогда,
поэтому присланное аудио провайдер не сохраняет; **результаты** распознавания
живут у него 3 суток, и система просит забыть их сразу после укладки текста.

**Без настройки ничего не уходит и ничего не ломается.** Умолчание
`CAIRN_TRANSCRIBER` — `off`: кнопки «Загрузить запись» нет вовсе, а на её
месте строка «Расшифровка записи не настроена». Внешнему адаптеру нужны
**и ключ, и каталог** (`x-folder-id` у SpeechKit не опционален), иначе порт
остаётся выключенным — карточка узла так и говорит: «Нет ключа», «Нет
каталога».

Узел настраивается с того же экрана «Настройки», что разбивка на задачи, и
база там тоже главнее окружения: правка действует **сразу, без перезапуска
API**, потому что адаптер строится на вызов, а не при подъёме. Два отличия
от узла разбивки, и оба названы:

- **вид «в вашем контуре» у этого узла не предлагается.** Своей службы
  распознавания в сборке нет, и настройка с таким видом сохранилась бы, а
  порт остался бы выключенным — то же правило, по которому не показывают
  кнопку загрузки при выключенной службе;
- **«Проверить связь» ничего не стоит.** Живой вызов распознавания означал
  бы отправку аудио и оплату, поэтому проверка спрашивает настроенный узел
  о **несуществующей операции**: ответ «не найдено» и есть успех — до узла
  дошли, ключ и каталог приняты. Ни байта записи и ни байта данных проекта
  наружу не уходит. Чего она не выясняет: возьмёт ли служба настоящую
  дорожку и хватит ли квоты.

**Без `ffmpeg` поток остаётся рабочим, только уже.** Это лестница из трёх
ступеней, и ни одна не ломает уже работающую возможность:

| Что настроено | Что принимается |
|---|---|
| ни ключа, ни `ffmpeg` | загрузки записи нет вовсе; текст набирается руками |
| ключ есть, `ffmpeg` нет | MP3, WAV и OGG — то, что служба берёт как есть; видео получает отказ `recording_needs_ffmpeg` |
| ключ и `ffmpeg` есть | всё перечисленное выше, включая видео |

В образе API `ffmpeg` есть (`apk add --no-cache ffmpeg` в ступени `runner`
`apps/api/Dockerfile`); отказаться от извлечения, не трогая образ, можно
настройкой `CAIRN_RECORDING_FFMPEG=off`. **Образ вырос на 175 МиБ** (184 МБ):
с 1,04 ГБ до 1,22 ГБ. Число измерено, а не оценено, — двумя сборками одного
коммита, со строкой `apk add` и без неё:

```bash
docker build -f apps/api/Dockerfile -t cairn-api:measure .
docker image inspect cairn-api:measure --format '{{.Size}}'   # байты, до и после
```

**Два предела, и они про разное.** Предел **загрузки** — 2 ГиБ
(`CAIRN_RECORDING_MAX_BYTES`), выведен из предела длительности у службы:
четыре часа видео в разумном качестве в него укладываются. Предел
**отправки** — 40 МиБ (`CAIRN_TRANSCRIBER_MAX_BYTES`), выведен из
провайдерского предела тела запроса (60 МБ) минус раздувание `base64`
(×1.33). После извлечения второй почти перестаёт быть границей: часовой
созвон в OGG/Opus моно 16 кГц — около 11 МБ, и упереться в предел может
только запись длиной почти четыре часа, то есть ровно та, которую служба и
так не возьмёт.

**Где лежат файлы и сколько это места.** Том `recordings-data`, в контейнере
смонтирован в `CAIRN_RECORDINGS_DIR` (по умолчанию `/var/lib/cairn/recordings`).
Загруженный исходник убирается, **когда текст уложен**; остаётся звуковая
дорожка — именно она хранится, пока живёт саммари. При **любой** неудаче
исходник остаётся: повторить попытку есть из чего. Переслушивать и
расшифровывать снова можно и после уборки — повтор работает с дорожкой и
минует `ffmpeg` целиком. Поэтому **запас диска считается по пику, а не по
покою**: в покое том держит единицы мегабайт на созвон, а пик равен пределу
загрузки на число идущих расшифровок — при одном тяжёлом шаге за тик это
единицы гигабайт. Запас всё равно нужен: на `ENOSPC` загрузка падает
названным отказом.

> **Записи не входят в резервную копию.** `scripts/backup.sh` копирует только
> базу (`pg_dump`), и это то же решение, по которому записи не лежат в базе:
> полгигабайта на созвон превратили бы ежедневную копию из единиц мегабайт в
> гигабайты. Восстановление из копии даёт **саммари, записей которых нет** —
> текст при этом на месте, он в базе. Нужны записи — копируй том отдельно.

**Четырнадцать переменных, и вот они все до одной** (первые шесть — узел, и
для них окружение лишь запасной источник; остальные восемь описывают наше
поведение и действуют всегда):

- `CAIRN_TRANSCRIBER` — вид службы: `off` (умолчание, порт выключен целиком
  при любом ключе), `external` (внешний API, первый — Yandex SpeechKit) или
  `local` (своя служба в контуре);
- `CAIRN_TRANSCRIBER_BASE_URL` — адрес службы. Пустое значение при `local`
  означает «выключено», а не «подставить внешний»: подстановка отправила бы
  запись созвона наружу у установки, которая выбрала свой контур;
- `CAIRN_TRANSCRIBER_API_KEY` — ключ. Пустой при `external` выключает порт:
  на свежей установке наружу не уходит ничего;
- `CAIRN_TRANSCRIBER_FOLDER_ID` — каталог Yandex Cloud, уходит заголовком
  `x-folder-id`. Внешнему адаптеру нужен так же обязательно, как ключ;
- `CAIRN_TRANSCRIBER_MODEL` — модель распознавания (умолчание `general`);
- `CAIRN_TRANSCRIBER_TIMEOUT_SECONDS` — сколько ждать **один обмен** со
  службой (умолчание `180`), не всю расшифровку;
- `CAIRN_TRANSCRIBER_MAX_BYTES` — предел **отправки** службе (умолчание
  `41943040`, 40 МиБ);
- `CAIRN_TRANSCRIPTION_POLL_SECONDS` — как часто идёт тик фонового прогона
  (умолчание `20`); `0` — цикл выключен, так работают тесты и локальная
  разработка;
- `CAIRN_TRANSCRIPTION_MAX_MINUTES` — сколько ждать одну расшифровку, прежде
  чем признать неудачей (умолчание `120`). Это про нашу меру ожидания, а не
  про провайдера: иначе строка висела бы вечно на операции, которой у него
  уже нет;
- `CAIRN_RECORDINGS_DIR` — каталог записей на томе (умолчание
  `/var/lib/cairn/recordings`);
- `CAIRN_RECORDING_MAX_BYTES` — предел **загрузки** (умолчание `2147483648`,
  2 ГиБ);
- `CAIRN_RECORDING_FFMPEG` — `auto` (искать в `PATH` при старте, умолчание),
  `off` (извлечение выключено решением администратора) или путь к
  исполняемому файлу;
- `CAIRN_RECORDING_AUDIO_BITRATE` — битрейт извлекаемой дорожки (умолчание
  `24k`), **не измеренный** на живом материале;
- `CAIRN_RECORDING_EXTRACT_MINUTES` — сколько ждать `ffmpeg`, прежде чем
  убить его (умолчание `30`).

Мусор и неположительное значение в числовых переменных означают умолчание, а
не «ждать вечно». Все четырнадцать перечислены в `.env.example` разделом
«Расшифровка записи созвона» и прокинуты в службу `api`.

Два числа и шесть подробностей, которые **ещё не проверены живьём**, — чтобы
тот, кто первым подключит ключ, знал, что смотреть (дизайн
`docs/superpowers/specs/2026-11-17-cairn-summary-transcription-design.md`,
раздел «Что требует живой проверки» и 11.1):

- **битрейт извлечения не измерен** на живом материале: 24 кбит/с выбраны
  арифметикой — при них четыре часа укладываются в предел отправки. Сравнить
  16, 24 и 32 кбит/с надо на **свежей** загрузке: переизвлечь дорожку у
  старого саммари нельзя, исходника больше нет;
- **к чему относится провайдерский предел 60 МБ** — к сырым байтам или к
  `base64`. Наши 40 МиБ взяты с запасом под оба прочтения;
- **регистр имён полей в REST** (`recognition_model` против
  `recognitionModel`): адаптер написан под `snake_case`, как в документации;
- **точные имена опций распознавания** (`text_normalization`,
  `language_restriction`, `audio_processing_type`) — до проверки адаптер их не
  отправляет и шлёт минимальный набор; с ними текст будет с пунктуацией и
  заметно читабельнее;
- **формат ответа `getRecognition`** — поток объектов, а не один JSON; разбор
  написан снисходительным именно потому, что формат не проверен. Первый живой
  ответ стоит сохранить в тест как есть, байт в байт;
- **поддерживается ли отмена операции** у провайдера: дизайн на неё не
  опирается — «Отменить» закрывает нашу задачу;
- **точный REST-путь удаления результатов**: в proto метод есть, в
  справочнике REST страница пустует. Если его нет — результаты истекут сами
  за 3 суток, и это названная граница, а не дефект.

## Выгрузка задач в трекер

У проекта есть реестр задач — экран «Задачи» под роадмапом
(`/projects/:id/roadmap/tasks`). Задача приходит двумя путями: её заводят
руками или она рождается релизом черновика саммари, — живёт между версиями и
попадает в версию отдельным действием. Чекпоинт версии перестал быть
формулировкой: он стал **размещением** задачи в версии, то есть парой «версия
× задача» с признаком «закрыт», позицией и памятью о переносе. Прогресс
версии по-прежнему вычисляется из чекпоинтов и только из них.

Задачи выгружаются во внешний трекер — Weeek. Право на выгрузку — **запись на
«Роадмап»**: новой единицы выдачи доступа не появилось, секций по-прежнему
шесть. Токен подключения принадлежит установке, а не проекту, поэтому его
задаёт суперадмин на том же экране «Настройки», что и службы модели.

**Лестница из четырёх ступеней, и ни одна не ломает уже работающую
возможность:**

| Что настроено | Что видно на экране «Задачи» |
|---|---|
| подключения не заводили вовсе | о выгрузке нет ни слова: ни кнопки, ни колонки, ни отметок |
| подключение есть, но не работает (нет токена, снята галочка, токен не расшифровывается) | колонка «Выгрузка» и выключенная кнопка с названной причиной; зеркала уже выгруженных задач остаются видны |
| подключение работает, доска не выбрана | кнопка выключена, причина названа и чинится на этом же экране — панель «Куда выгружать» |
| подключение работает и доска выбрана | «Выгрузить выбранные» уезжает отмеченным набором |

Первая строка — не умолчание ради краткости, а решение: колонка, в которой у
каждой строки «не выгружена», была бы на установке без трекера укором за
решение, которого никто не принимал. Вторая и третья, наоборот, называются
прямо: подключение кто-то начал настраивать и ждёт, что выгрузка работает.
**Установка без трекера работает целиком** — задачи заводятся, попадают в
версии и считаются в прогрессе ровно так же, прогон опроса не идёт, а ручка
выгрузки отвечает названным отказом (`tracker_not_configured`), а не
молчанием.

**Наружу уходит формулировка задачи, и только она.** Ни ссылки, которую
вписал человек, ни тегов платформ, ни имени проекта, ни окружений, ни
переменных, ни имени пользователя — в теле создания стоит один `title` и
идентификаторы доски из привязки. Это третье и последнее место, где
содержимое проекта покидает машину (два первых — разбивка саммари и
расшифровка записи созвона). Запись о передаче попадает в журнал **до первого
байта**, своей короткой транзакцией: нет записи — нет и передачи. Порядок
обратный («сходили, потом записали») терял бы ровно оборвавшиеся вызовы, то
есть те, о которых важнее всего знать.

За раз уезжает не больше 50 задач, и они идут **по очереди**, а не разом:
чужой API считает частоту. Первый отказ обмена останавливает набор —
остальные задачи получают исход «не пробовали», и это честнее, чем сорок
девять заведомо пустых походов в сеть и сорок девять записей журнала о
передаче, которой не было. Уже уехавшие при этом остаются выгруженными:
откат унёс бы зеркало задачи, которая в трекере уже лежит, и повтор завёл бы
там вторую. Ответ ручки — исход на каждую задачу, а не один код: «ничего не
вышло» на наборе, где три задачи уехали, заставило бы нажать повтор, то есть
править в трекере уже правильное.

**Пределов у набора два, и они про разное.** Пятьдесят задач — сколько можно
попросить за раз, и об этом сказано **до** нажатия. Срок ответа держит второй,
бюджет времени на сервере (50 секунд против умолчания `proxy_read_timeout`
nginx): длиной набора он не выражается — пятьдесят обменов по двадцать секунд
это шестнадцать минут в одной ручке, и за прокси человек получил бы `504`,
пока сервер ещё выгружает. Упёршись в бюджет, набор отвечает **целым**, а
задачи, до которых очередь не дошла, получают тот же исход «не пробовали» —
поэтому на экране он объяснён двумя разными фразами: когда в наборе был отказ
и когда не отказал никто. С недошедшими задачами не произошло ничего, отметки
с них не снимаются, и повтор — ровно то действие, которое нужно.

**Повторная выгрузка правит задачу в трекере** (`PUT /tm/tasks/{id}`), а не
создаёт вторую: ссылка на неё не меняется, доска не переносится, а «когда
выгрузили» остаётся первым разом. Ссылка `task.url`, которую вписал человек,
выгрузкой **не перезаписывается** никогда: ссылка на задачу в трекере живёт
своим полем, и одно поле на две ссылки затёрло бы заметку первой же
выгрузкой.

> **Статус из трекера — только зеркало. Он ничего не закрывает.** Чекпоинт
> закрывает человек, прогресс версии считается из чекпоинтов и только из них,
> а расхождение «в Weeek закрыто, здесь открыто» показывается биркой рядом с
> задачей — видно глазами и чинится одним нажатием. Автоматическое закрытие
> означало бы, что упавший опрос, снятый токен или переименованная колонка
> молча останавливают прогресс роадмапа.

**Статус запаздывает на интервал опроса, и это свойство их API, а не наша
недоработка:** вебхуков в публичном API Weeek нет вовсе (`/ws/webhooks`
отвечает `404`), поэтому узнать о чужой правке можно только спросив.
Спрашивает фоновый прогон раз в `CAIRN_TRACKER_POLL_SECONDS` (по умолчанию
300 секунд, `0` — цикл выключен), устроенный так же, как прогоны проверок
статуса и расшифровки: свой замок в базе, один тик за раз — ни в одном
процессе, ни в двух. Поэтому у каждой выгруженной задачи на экране
написано, **когда спрашивали**: без этой строки бирка утверждала бы, что
зеркало свежее. «Статус ещё не спрашивали» сказано отдельно от «не менялось» —
та же ошибка, что аптайм без пропусков наблюдения, и время проверки пишется
при **каждом** опросе, даже когда не изменилось ничего.

Чего прогон не делает и почему:

- **не идёт при подъёме приложения**, в отличие от прогона проверок статуса:
  там без первого тика только что вписанный адрес до четверти часа остаётся
  «неизвестно», а здесь зеркало уже лежит в базе и старше интервала не
  бывает — каждый перезапуск API стучался бы в чужой API ради знания, которое
  никуда не спешит;
- **не спрашивает о закрытых в трекере** задачах: закрытая задача не
  меняется, и спрашивать о ней каждые пять минут — платить трафиком за
  известное. Архивные проекты и проекты без привязки из обхода исключены
  тоже;
- **не пишет в журнал ничего**, и записи о передаче у него нет: наружу
  уходят идентификаторы доски, а не содержимое проекта. Запись «передали»
  стоит там, где уезжает формулировка.

Токен подключения устроен как ключ службы модели: шифруется тем же
`CAIRN_ENCRYPTION_KEY`, версий не имеет и **наружу не выходит никуда** — ни в
ответ ручки, ни в журнал, ни в текст отказа, ни в лог. Списки проектов, досок
и колонок трекера приходят на экран **через нашу ручку**, а не прямым
запросом из браузера, ровно по той же причине: токен не покидает сервер.
Запасного источника в окружении у подключения нет и не будет — у узлов модели
окружение осталось потому, что по прежнему README собраны работающие
установки, а подключения трекера не было никогда: второй источник пришлось
бы поддерживать ради пустого множества. Поэтому в `.env` у выгрузки ровно
одна переменная, и она про **наше** поведение, а не про провайдера.

Что попадает в журнал: `task.exported` и `task.export_updated` (выгрузка и
повторная выгрузка — разные события), `tracker.connection_updated`,
`tracker.secret_set`, `tracker.binding_set`, `tracker.probed`.

Две границы названы прямо:

- **удаление задачи в CAIRN не удаляет её в Weeek.** Удалять чужую задачу по
  своей кнопке мы не вправе; зеркало при удалении уносится, а идентификатор
  задачи в трекере остаётся в записи журнала `task.deleted` — других следов
  ответа на «а в трекере она осталась?» не остаётся. Смена доски выгрузки
  работает так же: уже выгруженные задачи остаются на прежней, в новую уедут
  только следующие. Снятие подключения уносит одной транзакцией и выбранные
  доски, и записи о выгрузках — иначе пережившая настройку запись утверждала
  бы, что в трекере лежит наша задача с известным номером, и после смены
  токена на другое пространство повторная выгрузка правила бы по этому номеру
  чужую задачу. Задачи проектов при этом остаются: трекер не владелец
  реестра;
- **теги платформ с тегами Weeek не сопоставляются.** В Weeek тег — числовой
  id пространства, у нас — название платформы проекта. Сопоставление возможно
  и будет ещё одной таблицей; без спроса её заводить нельзя.

Пять подробностей **не проверены живым токеном** (нужен токен рабочего
пространства; дизайн
`docs/superpowers/specs/2026-11-20-cairn-project-tasks-weeek-design.md`,
раздел 10.4) — чтобы тот, кто первым его подключит, знал, что смотреть:

- **формат человеческой ссылки на задачу.** Старшинство из трёх ступеней:
  ссылка берётся из ответа трекера, если она там есть; иначе собирается по
  шаблону `https://app.weeek.net/ws/<пространство>/task/<id>` — и только
  когда пространство задано в настройке; иначе её нет вовсе. **Проверен
  живьём только первый шаг**: шаблон угадан по виду их кабинета, поэтому он
  второй по старшинству, а не первый. Пустая ссылка честно означает «мы её не
  знаем», и бирка выгрузки на экране стоит и без неё;
- **принимает ли `POST /tm/tasks` поле `description`.** Пока не отправляется
  вовсе: у задачи CAIRN описания нет, и это вопрос на будущее, а не пробел;
- **есть ли у `GET /tm/tasks` фильтр по набору id.** Прогон спрашивает **по
  доске** — ветка, работающая в обоих случаях: один `GET` отвечает обо всех
  её задачах, а ответ сопоставляется по идентификатору. Найдётся фильтр —
  поменяется только адаптер;
- **пределы частоты запросов.** Отсюда и очередь вместо пачки, и предел
  набора в 50 задач, и пять минут вместо минуты у прогона: все три числа
  выбраны с запасом под неизвестный предел;
- **как называются параметры пагинации** у списков (`/tm/tasks`,
  `/tm/projects`, `/tm/boards`, `/tm/board-columns`). Списки читаются
  страницами, потому что иначе у доски длиннее одной страницы зеркало хвоста
  замерло бы навсегда, показывая при этом свежее «спрашивали только что», а
  доска, не попавшая в первую сотню, не выбиралась бы в привязке вовсе. Имена
  `perPage` и `offset` взяты как самые вероятные, и обход кончается, **даже
  если сервер их не понял**: страница короче просимой — последняя, страница с
  теми же идентификаторами означает, что смещение проигнорировано, а сверх
  этого стоит предел числа страниц (он про время тика, а не про полноту).
  Чего эта догадка не переживёт — отказа `4xx` на неизвестный параметр: тогда
  список откажет там, где однострочный запрос работал. Это единственный путь,
  которым пагинация способна ухудшить поведение, и смотреть на него надо
  первым.

## Первые шаги после установки

1. Открыть ссылку, выданную командой `create-superadmin`, и задать пароль.
2. Привязать второй фактор: до этого суперадмину доступен единственный экран
   `/security` — таково требование спеки 6.4, и ограничение проверяется на
   сервере, а не только в меню. Ключ показывается текстом: добавьте учётную
   запись в приложении-аутентификаторе вручную и подтвердите кодом.
3. Завести проект кнопкой «Создать проект» на сводке (доступна суперадмину)
   и заполнить паспорт.
4. Пригласить пользователей на экране «Пользователи» и выдать им доступ к
   секциям проекта на вкладке «Доступы».
5. Завести серверы на экране «Серверы», указать срок оплаты и привязать
   к ним окружения проектов — привязка доступна суперадмину.
6. Заполнить владельцев и сроки продления на экране «Домены»: сами корни
   заводятся автоматически по адресам окружений.
7. Настроить службу модели на экране «Настройки», если нужна разбивка
   саммари на задачи: адрес, схема авторизации, ключ и имя модели, затем
   «Проверить связь». Правка действует сразу, перезапуск не нужен; без
   настройки поток работает целиком, задачи набираются руками.
8. Подключить трекер задач там же, если нужна выгрузка: адрес, токен и
   пространство, затем «Проверить связь» — она читает пространство и ничего
   не создаёт. Доску для каждого проекта выбирает на своём экране «Задачи»
   тот, у кого есть запись на «Роадмап»: разные проекты — разные доски. Без
   подключения реестр задач работает целиком, выгрузки просто нет.

## Требования

Node.js 22, pnpm 10 (проще всего через `corepack enable` — версия берётся из
`packageManager` в корневом `package.json`), Docker.

Место на сервере: образ API — 1,22 ГБ (из них 175 МиБ — `ffmpeg`, нужный
расшифровке записей созвона), образ веба — около 0,5 ГБ, плюс том базы и том
записей. Запас под записи считается по пику загрузки, а не по покою — см.
«Расшифровка записи созвона».

## Локальная разработка

```bash
cp .env.example .env
openssl rand -base64 32   # вставить в CAIRN_ENCRYPTION_KEY
pnpm install
docker compose up -d --wait postgres
pnpm --filter @cairn/api db:migrate
pnpm --filter @cairn/api cli create-superadmin admin@example.com
```

Команда выведет ссылку на установку пароля. Затем в двух окнах:

```bash
pnpm --filter @cairn/api dev
CAIRN_ALLOW_INSECURE_NO_TOTP=1 pnpm --filter @cairn/web dev
```

Интерфейс — http://localhost:3000

Переменная задаётся в строке запуска, а не берётся из `.env`: Next читает
`.env` рядом с приложением, а не в корне монорепо, и флаг до веб-процесса
не доходит. Без него суперадмин без привязанного второго фактора упирается
в `/security` и дальше не идёт (см. «Второй фактор»).

### Миграции

Структурные изменения схемы заводятся обычным генератором:

```bash
pnpm --filter @cairn/api exec drizzle-kit generate --name=<имя>
```

В этом режиме снапшот в `apps/api/drizzle/meta` пишется по схеме, и
следующая миграция отсчитывается от него верно.

`--custom` — только для того, чего генератор не умеет: прав роли, переноса
данных, функций. В этом режиме снапшот копируется с предыдущего **без
оглядки на схему**, поэтому структурную правку руками обязательно
сопровождать выравниванием: отдельной `generate`-миграцией, SQL которой
опустошается (образец — `0025_snapshot_realign.sql`). Иначе первый же
`generate` выдаст чужие операторы вместе с новыми, а на схеме с новыми
таблицами ещё и спросит про переименование и повиснет без терминала.

Генератор задаёт вопросы интерактивно и требует настоящего терминала:
пайп и `script` ему не подходят.

## Проверки

```bash
pnpm test        # тесты; интеграционные поднимают PostgreSQL в контейнере
pnpm typecheck   # проверка типов
```

### Сквозная проверка

`pnpm e2e` проходит путь продукта целиком по **уже развёрнутой** системе: тем же
адресам и через тот же реверс-прокси, что и браузер. Тесты проверяют единицы
кода, эта проверка — что части соединяются: установка пароля по ссылке,
обязательная привязка второго фактора, создание проекта, приглашение, выдача
уровня «метаданные», журнал, отказы приглашённому и отзыв доступа.

Проверка заводит данные (проект, пользователя `guest@example.com`) и требует
неиспользованной ссылки суперадмина, поэтому запускать её следует на пустой
системе:

```bash
docker compose down -v
docker compose up -d --wait
docker compose run --rm api node dist/db/migrate.js
docker compose run --rm api node dist/cli/main.js create-superadmin admin@example.com
pnpm e2e '<ссылка из предыдущей команды>'
```

Адрес системы задаётся `CAIRN_BASE_URL` (по умолчанию `http://localhost`).
Локально прокси работает по HTTP: автоматический HTTPS выпустил бы на
`localhost` сертификат собственным центром Caddy, и браузер ругался бы на
него при каждом заходе. Боевой домен включает HTTPS переменной
`CAIRN_SCHEME=https` — тогда сертификат получает сам Caddy, а `CAIRN_BASE_URL`
указывают с `https://`.

## Развёртывание

Сборка идёт на самом сервере: реестр образов не нужен, внешних зависимостей
у развёртывания нет. Код попадает туда через `git pull`, всё остальное делает
`scripts/deploy.sh`, запускаемый на самой машине.

Требования к серверу: Ubuntu (проверено на 24.04) или другой Linux с Docker
Engine и плагином compose, 2 ГБ памяти с учётом подкачки (столько просит сборка
Next — на машине без запаса она падает по OOM) и 5 ГБ на диске.

### Подготовка сервера

Один раз на чистой машине:

```bash
# Docker из официального репозитория: в apt лежит устаревший docker.io
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"        # перезайти по ssh, чтобы группа применилась

sudo mkdir -p /opt/cairn && sudo chown "$USER" /opt/cairn
sudo ufw allow 22,80,443/tcp && sudo ufw enable
```

Если репозиторий закрытый, серверу нужен ключ только на чтение: `ssh-keygen -t
ed25519 -C cairn-server -f ~/.ssh/id_ed25519`, публичная часть добавляется в
репозиторий как deploy key.

Там же стоит авторизоваться в Docker Hub — оттуда берутся базовые образы
(`node`, `postgres`, `caddy`), и анонимным адресам он разрешает сотню скачиваний
за шесть часов. Исчерпанный лимит выглядит как `429 Too Many Requests` в самом
начале сборки; авторизация поднимает его вдвое и привязывает к учётной записи,
а не к адресу сервера:

```bash
docker login -u <логин>                # пароль — Access Token из hub.docker.com
```

Токен вместо пароля не прихоть: `docker login` сохраняет введённое в
`~/.docker/config.json` в открытом виде, и токен отзывается отдельно от учётной
записи. Сборка и без авторизации повторяет попытку трижды с растущей паузой —
случайный всплеск она переживёт сама.

### Первое развёртывание

На сервере:

```bash
git clone <адрес репозитория> /opt/cairn
cd /opt/cairn

cp .env.example .env
openssl rand -base64 32                # в CAIRN_ENCRYPTION_KEY
nano .env                              # пароли базы, домен, схема, адрес
```

В `.env` обязательны: `POSTGRES_PASSWORD`, `CAIRN_APP_PASSWORD`,
`CAIRN_ENCRYPTION_KEY`, `CAIRN_DOMAIN=<домен>`, `CAIRN_SCHEME=https`,
`CAIRN_WEB_URL=https://<домен>`. Файл в git не попадает и принадлежит серверу.
Копию ключа шифрования положи отдельно от сервера: без него зашифрованные
значения переменных не восстановить ни из какой резервной копии.

Домен должен указывать на сервер A-записью **до** развёртывания: Caddy получает
сертификат при старте, и без записи выпуск не пройдёт.

```bash
./scripts/deploy.sh
```

Скрипт проверит окружение, соберёт образы, применит миграции и поднимет систему.
Остаётся создать суперадмина — один раз:

```bash
docker compose -f docker-compose.yml run --rm api node dist/cli/main.js create-superadmin admin@example.com
```

Команда напечатает ссылку на установку пароля. По ней задаётся пароль, следом
система потребует привязать второй фактор — до этого доступен единственный
экран `/security`.

### Обновление

```bash
cd /opt/cairn
git pull
./scripts/deploy.sh                    # --no-cache пересобирает с нуля
```

`scripts/deploy.sh` делает шаги в таком порядке:

1. **проверки** (`scripts/preflight.sh`) — Docker, `.env`, вид ключа шифрования,
   согласованность домена, схемы и `CAIRN_WEB_URL`, запас памяти. Отдельно
   запрещён `CAIRN_ALLOW_INSECURE_NO_TOTP`: на развёрнутой системе флаг
   недопустим. Ключи VAPID проверяются по тем же правилам, что у `web-push`:
   незаданные — предупреждение (уведомления выключены осознанно), заданные
   наполовину или негодные — отказ, а годные при `CAIRN_SCHEME=http`
   предупреждают, что браузер не даст подписаться;
2. **резервная копия базы** — до того, как что-либо изменится (`--skip-backup`
   отключает);
3. **сборка образов**; предыдущие помечаются как `cairn-api:previous` и
   `cairn-web:previous` — на них возвращает откат;
4. **остановка `api` и `web`**, применение миграций, запуск. Миграции идут при
   остановленных приложениях: несколько секунд недоступности дешевле, чем старый
   код, работающий с новой схемой;
5. **проверка снаружи** — `GET /api/health` тем же адресом, что и браузер, то
   есть через прокси и с настоящим сертификатом.

`docker compose up --wait` дожидается именно готовности: у `api` и `web` есть
проверки живости, и прокси стартует после них, а не одновременно.

Развёртывание запускает compose с явным `-f docker-compose.yml`. Файл
`docker-compose.override.yml` compose подхватывает сам, и он публикует порт базы
наружу — это нужно рабочей машине (миграции и интеграционные тесты ходят в базу
с хоста) и вредно на сервере, где база доступна только по внутренней сети.

### Другие способы доставки кода

Git — основной путь. Два запасных на случай, когда он не подходит:

| | `git pull` + `deploy.sh` | `deploy-remote.sh` | `deploy-image.sh` |
|---|---|---|---|
| где собирается | на сервере | на сервере | на рабочей машине |
| что едет по сети | коммиты | рабочая копия целиком | образы (~1 ГБ, сжимаются вдвое) |
| требует от сервера | ~2 ГБ памяти под сборку | то же | только память под работу |
| незакоммиченные правки | не поедут | поедут | попадут в образ |

```bash
scripts/deploy-remote.sh cairn@example.com            # rsync рабочей копии, каталог /opt/cairn
scripts/deploy-image.sh  cairn@example.com --pull     # сборка здесь, docker save → docker load
```

`deploy-remote.sh` нужен, когда правки ещё не в git, а проверить их на сервере
надо сейчас. `deploy-image.sh` — когда сборка на сервере не проходит по памяти:
образ собирается там, где её хватает. Оба заканчиваются тем же `deploy.sh` на
сервере и не трогают `.env` — он принадлежит серверу.

### Резервные копии, откат, восстановление

```bash
scripts/backup.sh                                   # ./backups/cairn-ГГГГММДД-ЧЧММСС.dump
scripts/rollback.sh                                 # вернуть предыдущую сборку
scripts/restore.sh backups/cairn-20260916-120000.dump
```

Копии хранятся в количестве `CAIRN_BACKUP_KEEP` (по умолчанию 10). Ключ
`CAIRN_ENCRYPTION_KEY` в копию не входит намеренно: без него зашифрованные
значения переменных из дампа не восстановить — храни его отдельно.

Откат возвращает **только код**. Миграции необратимы: если развёртывание меняло
схему, вместе с откатом нужна и копия базы, снятая перед ним.

Реверс-прокси сводит интерфейс и API на один домен `CAIRN_DOMAIN`: только так
сессионная cookie остаётся first-party и CORS не нужен. Для настоящего домена
Caddy получает сертификат сам.

Если 80 и 443 на машине заняты другим прокси, задай `CAIRN_HTTP_PORT` и
`CAIRN_HTTPS_PORT`. На нестандартных портах открывай систему сразу по HTTPS-порту:
переадресация с HTTP ведёт на имя домена без порта. Порт должен попасть и в
`CAIRN_WEB_URL` — из него строятся ссылки приглашений.

### Развёртывание вручную

Скрипты — обёртка над обычными командами; при разборе поломки они делаются
по одной:

```bash
docker compose -f docker-compose.yml build
docker compose -f docker-compose.yml up -d --wait postgres
docker compose -f docker-compose.yml run --rm api node dist/db/migrate.js
docker compose -f docker-compose.yml up -d --wait
```

## Подключение агента

Агенты (Claude Code, Cursor и другие MCP-клиенты) подключаются к CAIRN только
на чтение. Токен выпускает суперадмин на экране доступов проекта; открытое
значение показывается один раз. Конфигурация клиента:

```json
{
  "url": "https://<домен>/api/mcp",
  "headers": { "Authorization": "Bearer <токен>" }
}
```

Профиль токена по умолчанию: инфо, документация, роадмап и хроника — чтение;
переменные и инфраструктура — только метаданные (ключи без значений). Доступ
к значениям переменных — отдельный флаг, выключенный по умолчанию: раскрытые
значения попадают в контекст модели агента. Каждый вызов инструмента
записывается в журнал с пометкой машинного субъекта.

## Второй фактор

Суперадмин обязан привязать второй фактор (TOTP) до работы с системой —
через его учётку доступны секреты всех проектов. Для локального стенда
требование можно снять переменной `CAIRN_ALLOW_INSECURE_NO_TOTP=1`
(сервис `web`); `preflight.sh` в этом случае громко предупреждает, но
развёртывание не останавливает — это решение владельца системы.

Флаг снимает только обязанность привязать фактор. Если фактор уже привязан,
вход продолжит требовать код: отвязать его можно командой
`reset-totp` (см. «Восстановление доступа»).

## Восстановление доступа

Если единственный суперадмин потерял пароль или устройство со вторым фактором:

```bash
docker compose run --rm api node dist/cli/main.js reset-password admin@example.com
docker compose run --rm api node dist/cli/main.js reset-totp admin@example.com
```

## Ключ шифрования

`CAIRN_ENCRYPTION_KEY` хранится отдельно от базы и не попадает в резервные копии
базы данных. При его потере зашифрованные значения восстановить невозможно —
это свойство схемы, а не дефект. Храните копию ключа отдельно.
