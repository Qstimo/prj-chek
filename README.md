# CAIRN

Единый реестр независимых проектов: где проект развёрнут, жив ли он, чем настроен,
что по нему решали и на какой стадии находится.

Реализованы этапы 1–10: аутентификация с двухфакторной проверкой, проекты
со всеми шестью секциями — «Инфо», «Инфраструктура», «Переменные»,
«Документация», «Роадмап», «Хроника» — модель выдач доступа, журнал
действий, автопроверки статуса.

Документация — Markdown-страницы «как это устроено сейчас» с безопасным
собственным рендером (HTML в тексте остаётся текстом); запись хроники
поднимается в чекпоинт роадмапа или страницу документации одним действием.

Серверы вынесены в отдельный реестр: машина заводится один раз, окружения
разных проектов на неё ссылаются, а экран «Серверы» показывает владельца,
статус и срок оплаты и предупреждает за две недели до его окончания.
Карта размещения `/servers/map` рисует граф «серверы → проекты»: видно,
что упадёт вместе с конкретной машиной. Реестр и карта доступны только
суперадмину — список машин межпроектен; подрядчик видит имя и параметры
лишь той машины, на которой стоит его окружение.

Домены ведутся тем же способом, что и серверы, но с одной поблажкой: корень
(`example.com`) появляется в реестре сам, как только подрядчик вписал адрес
стенда — ради адреса не нужно дёргать владельца реестра. Владельца,
регистратора и срок продления задаёт суперадмин на экране «Домены»;
предупреждение приходит за месяц, а не за две недели, потому что
освободившийся домен могут перехватить в тот же день. Карта `/domains/map`
показывает, какие проекты держатся на каком корне.

Статус проектов обновляется сам: система опрашивает health-check адреса
окружений, следит за сроками TLS-сертификатов и регистрации доменов
(интервал — `CAIRN_STATUS_CHECK_INTERVAL_MINUTES`, по умолчанию 15 минут,
`0` — выключено), а сводка показывает индикаторы и предупреждения о сроках.
Руками задаётся только «приостановлен» — через жизненный цикл проекта.

Роадмап — последовательность версий с чекпоинтами: прогресс вычисляется,
диаграмма показывает стадию за две секунды, а суперадмин может опубликовать
роадмап наружу по ссылке `/roadmap/<токен>` — единственная публичная
страница системы; отключение ссылки гасит её немедленно. Запись хроники
поднимается в чекпоинт одним действием.

Переменные — самая чувствительная секция: значения шифруются ключом
`CAIRN_ENCRYPTION_KEY`, живущим вне базы; каждое изменение создаёт новую
версию с возможностью отката; значение никогда не попадает в списки и
раскрывается только отдельным действием с записью в журнал; `.env`
импортируется и выгружается одним действием (выгрузка тоже фиксируется
в журнале). Уровень «метаданные» показывает, какие переменные нужны
проекту, не показывая их значений.

У проекта есть уникальный приёмный адрес: внешний инструмент отправляет
сводку POST-запросом (JSON с полем `content` или чистый текст) — и она
появляется в хронике с пометкой источника. Адрес создаёт и отзывает
суперадмин на странице хроники; приём почты на тот же адрес появится позже.
Автопроверки статуса окружений — этап 6.

## Первые шаги после установки

1. Открыть ссылку, выданную командой `create-superadmin`, и задать пароль.
2. Привязать второй фактор: до этого суперадмину доступен единственный экран
   `/security` — таково требование спеки 6.4, и ограничение проверяется на
   сервере, а не только в меню. Ключ показывается текстом: добавьте учётную
   запись в приложении-аутентификаторе вручную и подтвердите кодом.
3. Завести проект кнопкой «Создать проект» на сводке (доступна суперадмину)
   и заполнить паспорт.
4. Пригласить пользователей на экране «Пользователи» и выдать им доступ к
   секциям проекта на вкладке «Доступы».
5. Завести серверы на экране «Серверы», указать срок оплаты и привязать
   к ним окружения проектов — привязка доступна суперадмину.
6. Заполнить владельцев и сроки продления на экране «Домены»: сами корни
   заводятся автоматически по адресам окружений.

## Требования

Node.js 22, pnpm 10 (проще всего через `corepack enable` — версия берётся из
`packageManager` в корневом `package.json`), Docker.

## Локальная разработка

```bash
cp .env.example .env
openssl rand -base64 32   # вставить в CAIRN_ENCRYPTION_KEY
pnpm install
docker compose up -d --wait postgres
pnpm --filter @cairn/api db:migrate
pnpm --filter @cairn/api cli create-superadmin admin@example.com
```

Команда выведет ссылку на установку пароля. Затем в двух окнах:

```bash
pnpm --filter @cairn/api dev
pnpm --filter @cairn/web dev
```

Интерфейс — http://localhost:3000

## Проверки

```bash
pnpm test        # тесты; интеграционные поднимают PostgreSQL в контейнере
pnpm typecheck   # проверка типов
```

### Сквозная проверка

`pnpm e2e` проходит путь продукта целиком по **уже развёрнутой** системе: тем же
адресам и через тот же реверс-прокси, что и браузер. Тесты проверяют единицы
кода, эта проверка — что части соединяются: установка пароля по ссылке,
обязательная привязка второго фактора, создание проекта, приглашение, выдача
уровня «метаданные», журнал, отказы приглашённому и отзыв доступа.

Проверка заводит данные (проект, пользователя `guest@example.com`) и требует
неиспользованной ссылки суперадмина, поэтому запускать её следует на пустой
системе:

```bash
docker compose down -v
docker compose up -d --wait
docker compose run --rm api node dist/db/migrate.js
docker compose run --rm api node dist/cli/main.js create-superadmin admin@example.com
pnpm e2e '<ссылка из предыдущей команды>'
```

Адрес системы задаётся `CAIRN_BASE_URL` (по умолчанию `http://localhost`).
Локально прокси работает по HTTP: автоматический HTTPS выпустил бы на
`localhost` сертификат собственным центром Caddy, и браузер ругался бы на
него при каждом заходе. Боевой домен включает HTTPS переменной
`CAIRN_SCHEME=https` — тогда сертификат получает сам Caddy, а `CAIRN_BASE_URL`
указывают с `https://`.

## Развёртывание

Сборка идёт на самом сервере: реестр образов не нужен, внешних зависимостей
у развёртывания нет. Код попадает туда через `git pull`, всё остальное делает
`scripts/deploy.sh`, запускаемый на самой машине.

Требования к серверу: Ubuntu (проверено на 24.04) или другой Linux с Docker
Engine и плагином compose, 2 ГБ памяти с учётом подкачки (столько просит сборка
Next — на машине без запаса она падает по OOM) и 5 ГБ на диске.

### Подготовка сервера

Один раз на чистой машине:

```bash
# Docker из официального репозитория: в apt лежит устаревший docker.io
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker "$USER"        # перезайти по ssh, чтобы группа применилась

sudo mkdir -p /opt/cairn && sudo chown "$USER" /opt/cairn
sudo ufw allow 22,80,443/tcp && sudo ufw enable
```

Если репозиторий закрытый, серверу нужен ключ только на чтение: `ssh-keygen -t
ed25519 -C cairn-server -f ~/.ssh/id_ed25519`, публичная часть добавляется в
репозиторий как deploy key.

### Первое развёртывание

На сервере:

```bash
git clone <адрес репозитория> /opt/cairn
cd /opt/cairn

cp .env.example .env
openssl rand -base64 32                # в CAIRN_ENCRYPTION_KEY
nano .env                              # пароли базы, домен, схема, адрес
```

В `.env` обязательны: `POSTGRES_PASSWORD`, `CAIRN_APP_PASSWORD`,
`CAIRN_ENCRYPTION_KEY`, `CAIRN_DOMAIN=<домен>`, `CAIRN_SCHEME=https`,
`CAIRN_WEB_URL=https://<домен>`. Файл в git не попадает и принадлежит серверу.
Копию ключа шифрования положи отдельно от сервера: без него зашифрованные
значения переменных не восстановить ни из какой резервной копии.

Домен должен указывать на сервер A-записью **до** развёртывания: Caddy получает
сертификат при старте, и без записи выпуск не пройдёт.

```bash
./scripts/deploy.sh
```

Скрипт проверит окружение, соберёт образы, применит миграции и поднимет систему.
Остаётся создать суперадмина — один раз:

```bash
docker compose -f docker-compose.yml run --rm api node dist/cli/main.js create-superadmin admin@example.com
```

Команда напечатает ссылку на установку пароля. По ней задаётся пароль, следом
система потребует привязать второй фактор — до этого доступен единственный
экран `/security`.

### Обновление

```bash
cd /opt/cairn
git pull
./scripts/deploy.sh                    # --no-cache пересобирает с нуля
```

`scripts/deploy.sh` делает шаги в таком порядке:

1. **проверки** (`scripts/preflight.sh`) — Docker, `.env`, вид ключа шифрования,
   согласованность домена, схемы и `CAIRN_WEB_URL`, запас памяти. Отдельно
   запрещён `CAIRN_ALLOW_INSECURE_NO_TOTP`: на развёрнутой системе флаг
   недопустим;
2. **резервная копия базы** — до того, как что-либо изменится (`--skip-backup`
   отключает);
3. **сборка образов**; предыдущие помечаются как `cairn-api:previous` и
   `cairn-web:previous` — на них возвращает откат;
4. **остановка `api` и `web`**, применение миграций, запуск. Миграции идут при
   остановленных приложениях: несколько секунд недоступности дешевле, чем старый
   код, работающий с новой схемой;
5. **проверка снаружи** — `GET /api/health` тем же адресом, что и браузер, то
   есть через прокси и с настоящим сертификатом.

`docker compose up --wait` дожидается именно готовности: у `api` и `web` есть
проверки живости, и прокси стартует после них, а не одновременно.

Развёртывание запускает compose с явным `-f docker-compose.yml`. Файл
`docker-compose.override.yml` compose подхватывает сам, и он публикует порт базы
наружу — это нужно рабочей машине (миграции и интеграционные тесты ходят в базу
с хоста) и вредно на сервере, где база доступна только по внутренней сети.

### Другие способы доставки кода

Git — основной путь. Два запасных на случай, когда он не подходит:

| | `git pull` + `deploy.sh` | `deploy-remote.sh` | `deploy-image.sh` |
|---|---|---|---|
| где собирается | на сервере | на сервере | на рабочей машине |
| что едет по сети | коммиты | рабочая копия целиком | образы (~1 ГБ, сжимаются вдвое) |
| требует от сервера | ~2 ГБ памяти под сборку | то же | только память под работу |
| незакоммиченные правки | не поедут | поедут | попадут в образ |

```bash
scripts/deploy-remote.sh cairn@example.com            # rsync рабочей копии, каталог /opt/cairn
scripts/deploy-image.sh  cairn@example.com --pull     # сборка здесь, docker save → docker load
```

`deploy-remote.sh` нужен, когда правки ещё не в git, а проверить их на сервере
надо сейчас. `deploy-image.sh` — когда сборка на сервере не проходит по памяти:
образ собирается там, где её хватает. Оба заканчиваются тем же `deploy.sh` на
сервере и не трогают `.env` — он принадлежит серверу.

### Резервные копии, откат, восстановление

```bash
scripts/backup.sh                                   # ./backups/cairn-ГГГГММДД-ЧЧММСС.dump
scripts/rollback.sh                                 # вернуть предыдущую сборку
scripts/restore.sh backups/cairn-20260916-120000.dump
```

Копии хранятся в количестве `CAIRN_BACKUP_KEEP` (по умолчанию 10). Ключ
`CAIRN_ENCRYPTION_KEY` в копию не входит намеренно: без него зашифрованные
значения переменных из дампа не восстановить — храни его отдельно.

Откат возвращает **только код**. Миграции необратимы: если развёртывание меняло
схему, вместе с откатом нужна и копия базы, снятая перед ним.

Реверс-прокси сводит интерфейс и API на один домен `CAIRN_DOMAIN`: только так
сессионная cookie остаётся first-party и CORS не нужен. Для настоящего домена
Caddy получает сертификат сам.

Если 80 и 443 на машине заняты другим прокси, задай `CAIRN_HTTP_PORT` и
`CAIRN_HTTPS_PORT`. На нестандартных портах открывай систему сразу по HTTPS-порту:
переадресация с HTTP ведёт на имя домена без порта. Порт должен попасть и в
`CAIRN_WEB_URL` — из него строятся ссылки приглашений.

### Развёртывание вручную

Скрипты — обёртка над обычными командами; при разборе поломки они делаются
по одной:

```bash
docker compose -f docker-compose.yml build
docker compose -f docker-compose.yml up -d --wait postgres
docker compose -f docker-compose.yml run --rm api node dist/db/migrate.js
docker compose -f docker-compose.yml up -d --wait
```

## Подключение агента

Агенты (Claude Code, Cursor и другие MCP-клиенты) подключаются к CAIRN только
на чтение. Токен выпускает суперадмин на экране доступов проекта; открытое
значение показывается один раз. Конфигурация клиента:

```json
{
  "url": "https://<домен>/api/mcp",
  "headers": { "Authorization": "Bearer <токен>" }
}
```

Профиль токена по умолчанию: инфо, документация, роадмап и хроника — чтение;
переменные и инфраструктура — только метаданные (ключи без значений). Доступ
к значениям переменных — отдельный флаг, выключенный по умолчанию: раскрытые
значения попадают в контекст модели агента. Каждый вызов инструмента
записывается в журнал с пометкой машинного субъекта.

## Второй фактор

Суперадмин обязан привязать второй фактор (TOTP) до работы с системой —
через его учётку доступны секреты всех проектов. Для локального стенда
требование можно снять переменной `CAIRN_ALLOW_INSECURE_NO_TOTP=1`
(сервис `web`); `preflight.sh` в этом случае громко предупреждает, но
развёртывание не останавливает — это решение владельца системы.

Флаг снимает только обязанность привязать фактор. Если фактор уже привязан,
вход продолжит требовать код: отвязать его можно командой
`reset-totp` (см. «Восстановление доступа»).

## Восстановление доступа

Если единственный суперадмин потерял пароль или устройство со вторым фактором:

```bash
docker compose run --rm api node dist/cli/main.js reset-password admin@example.com
docker compose run --rm api node dist/cli/main.js reset-totp admin@example.com
```

## Ключ шифрования

`CAIRN_ENCRYPTION_KEY` хранится отдельно от базы и не попадает в резервные копии
базы данных. При его потере зашифрованные значения восстановить невозможно —
это свойство схемы, а не дефект. Храните копию ключа отдельно.
