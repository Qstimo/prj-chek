# CAIRN

Единый реестр независимых проектов: где проект развёрнут, жив ли он, чем настроен,
что по нему решали и на какой стадии находится.

Реализованы этапы 1–7: аутентификация с двухфакторной проверкой, проекты
со всеми шестью секциями — «Инфо», «Инфраструктура», «Переменные»,
«Документация», «Роадмап», «Хроника» — модель выдач доступа, журнал
действий, автопроверки статуса.

Документация — Markdown-страницы «как это устроено сейчас» с безопасным
собственным рендером (HTML в тексте остаётся текстом); запись хроники
поднимается в чекпоинт роадмапа или страницу документации одним действием.

Статус проектов обновляется сам: система опрашивает health-check адреса
окружений, следит за сроками TLS-сертификатов и регистрации доменов
(интервал — `CAIRN_STATUS_CHECK_INTERVAL_MINUTES`, по умолчанию 15 минут,
`0` — выключено), а сводка показывает индикаторы и предупреждения о сроках.
Руками задаётся только «приостановлен» — через жизненный цикл проекта.

Роадмап — последовательность версий с чекпоинтами: прогресс вычисляется,
диаграмма показывает стадию за две секунды, а суперадмин может опубликовать
роадмап наружу по ссылке `/roadmap/<токен>` — единственная публичная
страница системы; отключение ссылки гасит её немедленно. Запись хроники
поднимается в чекпоинт одним действием.

Переменные — самая чувствительная секция: значения шифруются ключом
`CAIRN_ENCRYPTION_KEY`, живущим вне базы; каждое изменение создаёт новую
версию с возможностью отката; значение никогда не попадает в списки и
раскрывается только отдельным действием с записью в журнал; `.env`
импортируется и выгружается одним действием (выгрузка тоже фиксируется
в журнале). Уровень «метаданные» показывает, какие переменные нужны
проекту, не показывая их значений.

У проекта есть уникальный приёмный адрес: внешний инструмент отправляет
сводку POST-запросом (JSON с полем `content` или чистый текст) — и она
появляется в хронике с пометкой источника. Адрес создаёт и отзывает
суперадмин на странице хроники; приём почты на тот же адрес появится позже.
Автопроверки статуса окружений — этап 6.

## Первые шаги после установки

1. Открыть ссылку, выданную командой `create-superadmin`, и задать пароль.
2. Привязать второй фактор: до этого суперадмину доступен единственный экран
   `/security` — таково требование спеки 6.4, и ограничение проверяется на
   сервере, а не только в меню. Ключ показывается текстом: добавьте учётную
   запись в приложении-аутентификаторе вручную и подтвердите кодом.
3. Завести проект кнопкой «Создать проект» на сводке (доступна суперадмину)
   и заполнить паспорт.
4. Пригласить пользователей на экране «Пользователи» и выдать им доступ к
   секциям проекта на вкладке «Доступы».

## Требования

Node.js 22, pnpm 10 (проще всего через `corepack enable` — версия берётся из
`packageManager` в корневом `package.json`), Docker.

## Локальная разработка

```bash
cp .env.example .env
openssl rand -base64 32   # вставить в CAIRN_ENCRYPTION_KEY
pnpm install
docker compose up -d --wait postgres
pnpm --filter @cairn/api db:migrate
pnpm --filter @cairn/api cli create-superadmin admin@example.com
```

Команда выведет ссылку на установку пароля. Затем в двух окнах:

```bash
pnpm --filter @cairn/api dev
pnpm --filter @cairn/web dev
```

Интерфейс — http://localhost:3000

## Проверки

```bash
pnpm test        # тесты; интеграционные поднимают PostgreSQL в контейнере
pnpm typecheck   # проверка типов
```

### Сквозная проверка

`pnpm e2e` проходит путь продукта целиком по **уже развёрнутой** системе: тем же
адресам и через тот же реверс-прокси, что и браузер. Тесты проверяют единицы
кода, эта проверка — что части соединяются: установка пароля по ссылке,
обязательная привязка второго фактора, создание проекта, приглашение, выдача
уровня «метаданные», журнал, отказы приглашённому и отзыв доступа.

Проверка заводит данные (проект, пользователя `guest@example.com`) и требует
неиспользованной ссылки суперадмина, поэтому запускать её следует на пустой
системе:

```bash
docker compose down -v
docker compose up -d --wait
docker compose run --rm api node dist/db/migrate.js
docker compose run --rm api node dist/cli/main.js create-superadmin admin@example.com
pnpm e2e '<ссылка из предыдущей команды>'
```

Адрес системы задаётся `CAIRN_BASE_URL` (по умолчанию `https://localhost`).
Против локального Caddy сертификат выпущен его собственным центром, поэтому
понадобится `CAIRN_INSECURE_TLS=1`; против настоящего домена эту переменную
задавать нельзя — проверка сертификата тоже часть проверки.

## Развёртывание

```bash
docker compose build
docker compose up -d --wait
docker compose run --rm api node dist/db/migrate.js
docker compose run --rm api node dist/cli/main.js create-superadmin admin@example.com
```

Реверс-прокси сводит интерфейс и API на один домен `CAIRN_DOMAIN`: только так
сессионная cookie остаётся first-party и CORS не нужен. Для настоящего домена
Caddy получает сертификат сам.

Если 80 и 443 на машине заняты другим прокси, задай `CAIRN_HTTP_PORT` и
`CAIRN_HTTPS_PORT`. На нестандартных портах открывай систему сразу по HTTPS-порту:
переадресация с HTTP ведёт на имя домена без порта. Порт должен попасть и в
`CAIRN_WEB_URL` — из него строятся ссылки приглашений.

## Подключение агента

Агенты (Claude Code, Cursor и другие MCP-клиенты) подключаются к CAIRN только
на чтение. Токен выпускает суперадмин на экране доступов проекта; открытое
значение показывается один раз. Конфигурация клиента:

```json
{
  "url": "https://<домен>/api/mcp",
  "headers": { "Authorization": "Bearer <токен>" }
}
```

Профиль токена по умолчанию: инфо, документация, роадмап и хроника — чтение;
переменные и инфраструктура — только метаданные (ключи без значений). Доступ
к значениям переменных — отдельный флаг, выключенный по умолчанию: раскрытые
значения попадают в контекст модели агента. Каждый вызов инструмента
записывается в журнал с пометкой машинного субъекта.

## Второй фактор

Суперадмин обязан привязать второй фактор (TOTP) до работы с системой —
через его учётку доступны секреты всех проектов. Для локального стенда
требование можно снять переменной `CAIRN_ALLOW_INSECURE_NO_TOTP=1`
(сервис `web`). На боевом развёртывании флаг недопустим.

## Восстановление доступа

Если единственный суперадмин потерял пароль или устройство со вторым фактором:

```bash
docker compose run --rm api node dist/cli/main.js reset-password admin@example.com
docker compose run --rm api node dist/cli/main.js reset-totp admin@example.com
```

## Ключ шифрования

`CAIRN_ENCRYPTION_KEY` хранится отдельно от базы и не попадает в резервные копии
базы данных. При его потере зашифрованные значения восстановить невозможно —
это свойство схемы, а не дефект. Храните копию ключа отдельно.
