## Что такое CAIRN

Единый реестр независимых проектов: где проект развёрнут, жив ли он, чем настроен, что по нему решали, на какой стадии он находится. Единица учёта — **проект** (не окружение, как в менеджерах секретов, и не клиент, как в MSP-платформах).

У проекта шесть секций (закрытый список — секции являются единицами выдачи доступа):

1. **Инфо** — паспорт проекта, жизненный цикл (задаётся вручную, означает намерение).
2. **Инфраструктура** — окружения (прод/стейдж/дев), двухуровневая схема «проект → окружение» обязательна.
3. **Переменные** — самая чувствительная сущность: шифрование на уровне приложения, версионирование с откатом, значения раскрываются только отдельным действием с записью в журнал, импорт/выгрузка `.env`.
4. **Документация** — «как это устроено сейчас».
5. **Роадмап** — версии с чекпоинтами; прогресс вычисляется, не хранится. Единственная секция с публичной ссылкой.
6. **Хроника** — «как мы к этому пришли»; не смешивать с документацией.

## Архитектурные инварианты

Это жёсткие решения из ТЗ, а не пожелания:

- **Единая модель прав для людей и машин.** Три вида субъектов (пользователь, токен агента, приёмный адрес) живут в одной таблице выдач «субъект × проект × секция × уровень». Отдельной системы прав для машин быть не должно.
- **Четыре уровня доступа**: нет / метаданные / чтение / запись. «Нет» означает, что существование секции (и даже проекта) не раскрывается. Уровень «метаданные» существует прежде всего ради переменных: видеть список ключей, не видя значений.
- **Проверка прав — единой функцией на уровне выборки данных**, не в интерфейсе и не в компонентах. Это обязательное требование ТЗ (раздел 4.1).
- **Журнал действий — неизменяемый, только на добавление**: кто, что, когда, над чем, человек или машина. Каждое раскрытие значения переменной — в журнал.
- **Агенты (MCP) — только чтение, никакой записи.** Профиль токена по умолчанию закрытый; доступ к значениям переменных — отдельная явная настройка, выключенная по умолчанию (риск утечки через контекст модели и внедрения инструкций через документацию — раздел 7.4).
- **Приёмный канал** — уникальный адрес проекта (почта + webhook); принадлежность проекту определяется адресом, без распознавания. Предложения модели (документация/чекпоинты из сводки) применяются только после подтверждения человеком.
- **Статус — автоматический** (health-check, TLS, срок домена), руками задаётся только «приостановлен».
- **Вне объёма** (раздел 1.4 — условие жизнеспособности продукта): задачи с исполнителями, трекинг времени, финансы, тикеты, комментарии, спринты. Чекпоинты роадмапа — без исполнителей, оценок, дат и вложенности.

## Нефункциональные ограничения

- Self-hosted, без внешних зависимостей для основной работы.
- Ключ шифрования хранится отдельно от базы; 2FA для суперадмина; секреты не попадают в логи и списочные ответы.
- Масштаб: десятки проектов, единицы пользователей — простота важнее производительности.

## Порядок реализации

Восемь этапов (раздел 10 ТЗ), после каждого — рабочий продукт. Ключевое: модель прав и понятие машинного субъекта проектируются на этапе 1 («Фундамент») — переделывать их на системе с живыми секретами крайне болезненно. Переменные — этап 4, MCP-доступ — последний, этап 8.
